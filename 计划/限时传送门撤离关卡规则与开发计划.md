# 限时传送门撤离关卡规则与开发计划

## 1. 文档定位

本方案把传送门定义为战斗关卡的“限时撤离目标”：玩家必须在倒计时结束前，让全部仍存活、仍受玩家控制的战斗单位进入撤离区，才能通关；否则判定失败。

本阶段只完成资源审查和规则设计，不导入资源、不修改战斗代码。

## 2. 资源包审查结论

资源包 `Portal Effect URP 1.0.unitypackage` 约 3.35 MB，包含：

- `PortalTunnelStarter.prefab`：基础双端传送门预制体。
- `PortalTunnel.prefab`、演示场景和演示模型。
- `PortalOpen.anim`、`PortalClose.anim` 和 `Portal.controller`。
- `PortalView`：用额外相机和 RenderTexture 显示门另一侧画面。
- `PortalTransition`：让物体从入口传送到出口。
- `PortalAnimation`、`PortalPhysicsAffector`、`PortalOptimization`。
- 传送门、边框、扭曲、粒子等材质、纹理与 Shader。

资源说明要求使用原生 `PortalTransition` 的物体具有 Rigidbody、Collider，并通过触发器进入传送流程。这与当前项目“格子位置、无单位物理碰撞、编队整体下令”的战斗结构不一致。因此：

1. 复用传送门模型、材质、粒子和开关动画。
2. 不直接用 `PortalTransition` 判定通关，也不把 Rigidbody/Collider 强加给战斗单位。
3. 新建基于格子坐标的 `PortalExtractionZone` 负责进入、撤离和胜负判定。
4. `PortalView` 的双相机实时画面不是 MVP 必需项，默认关闭，以免增加渲染成本；首版使用发光、粒子和旋转纹理表达开启状态。

注意：包名标注 URP，但随包说明标题仍写 HDRP；当前项目清单没有显式安装 URP/HDRP 包。导入后必须先在隔离验证场景检查 Shader 编译、透明排序和材质粉色问题，再决定保留原 Shader 或制作项目兼容材质。不得直接把演示场景合并进 `BattleScene`。

## 3. 推荐的正式玩法规则

### 3.1 目标单位范围

通关要求为：倒计时结束前，全部“仍存活且尚未撤离”的玩家普通战斗单位完成撤离。

- 已死亡单位计入战损，但不再要求进入传送门。
- 已进入传送门的单位标记为 `Extracted`，不再受伤、寻路、攻击或占用地图格。
- 指挥官当前只有逻辑锚点和头像标记，不作为独立撤离对象；其编队最后一名单位撤离后，该指挥官随编队完成撤离。
- 召唤物、疑兵分身、临时投射物不计入必须撤离数量。
- 战斗中生产并正式加入玩家编队的永久单位计入撤离数量。

### 3.2 时间规则

- 倒计时从玩家点击“开始战斗”、战斗阶段切换到 `Combat` 时开始。
- 部署和布阵阶段不扣时间。
- 建议首个验证关卡使用 180 秒，最终数值由关卡配置决定。
- UI 始终显示 `剩余时间` 和 `已撤离 / 需撤离`。
- 剩余 30 秒时变为黄色并提示一次；剩余 10 秒时变为红色并每秒脉冲。
- 暂停游戏时倒计时暂停；结算界面打开后停止计时。

### 3.3 胜利与失败

胜利条件：

```text
Combat 阶段已开始
且至少有一个有效玩家单位曾参与本关
且当前需要撤离的所有存活玩家单位均已进入传送门
```

失败条件：

```text
倒计时归零时仍有任何存活玩家单位未撤离
或所有玩家编队在完成撤离前被消灭
```

优先级规定：同一逻辑帧中先处理单位进入撤离区，再处理倒计时归零。最后一个单位在 `0.00` 秒所在帧成功进入时，判定胜利，避免视觉上到达却失败。

敌人全部被消灭不再直接胜利。此时战斗继续，玩家仍需在剩余时间内撤离。可显示“敌军已肃清，前往传送门”。

### 3.4 传送门状态

建议状态机：

```text
Dormant -> Opening -> Active -> Completing -> Closed
                         |            |
                         +-> Failed <-+
```

- `Dormant`：部署阶段存在但未激活，可用低亮度轮廓提示目标。
- `Opening`：战斗开始播放开门动画，短暂期间不可进入，建议 0.8-1.2 秒。
- `Active`：允许玩家单位进入并撤离。
- `Completing`：最后一个必需单位进入，锁定输入并播放完成动画。
- `Failed`：超时或玩家全灭，传送门熄灭/关闭。
- `Closed`：结算后停止粒子与额外渲染。

### 3.5 进入判定

传送门占用一个独立的逻辑撤离区，推荐首版为 2×2 格：

- 撤离区必须在地图边界内、全部可通行，且不能与建筑、部署格或永久障碍重叠。
- 玩家点击传送门或撤离区时，仍通过 `CommanderGroupCommandController` 给当前激活编队下达整体移动命令，禁止直接控制单兵。
- 编队抵达后，成员按各自阵型槽位依次进入有效格；每名单位单独触发撤离表现。
- 单位到达撤离格中心容差范围后才算进入，不能只靠模型与特效视觉重叠。
- 敌方单位可以经过或封锁附近格，但不能触发撤离。

### 3.6 编队撤离规则

- 一次仍只激活并指挥一名指挥官编队。
- 一个编队可分批撤离；已撤离成员从该编队的可执行成员列表移除，但不能被当作死亡。
- 剩余成员继续保持原 `FormationSlotIndex`，必要时围绕当前锚点压缩合法槽位，不重新开放单兵控制。
- 编队全部成员死亡：状态为 `Defeated`。
- 编队全部非死亡成员撤离：状态为 `Extracted`，地图指挥官头像淡出并停止接收命令。
- 如果仍有其他玩家编队未撤离，自动激活下一支未撤离编队；没有下一支时进入胜利结算。

## 4. 地图生成与放置规则

随机地图生成增加传送门出口规划步骤，位于地形、建筑、道路和部署区域确定之后：

1. 收集可通行且能容纳完整 2×2 撤离区的候选锚点。
2. 排除玩家/敌人部署区、建筑占地和地图边缘裁切位置。
3. 使用寻路验证至少存在一条从每个玩家部署区到撤离区的路线。
4. 候选点与玩家初始部署区保持最低路径距离，避免开局即撤离；也不能远到超过时间预算。
5. 在固定种子下稳定选择同一位置，写入 `GeneratedMapData` 和地图哈希输入。
6. 找不到合法位置时，该种子生成失败并进入现有重试流程，不能把门强行放在水面或建筑上。

建议新增配置：

```text
EnableExtractionPortal
ExtractionTimeLimitSeconds
ExtractionZoneWidth / Height
MinPortalPathDistanceFromPlayer
MaxPortalPathDistanceFromPlayer
PortalOpeningDelaySeconds
```

随机地图工具应显示传送门标记、路径距离和可达性校验结果，并把“传送门不可达/与建筑重叠/距离越界”纳入批量验证。

## 5. 数据与代码结构

建议新增：

- `ExtractionObjectiveDefinition`：关卡静态配置。
- `PortalSpawnData`：随机地图生成结果中的位置、朝向和占地。
- `PortalExtractionZone`：格子进入检测、视觉状态和撤离事件。
- `ExtractionObjectiveController`：倒计时、数量统计、状态机和胜负请求。
- `UnitExitState`：`Active / Extracting / Extracted`，与 `UnitState.Dead` 分离。
- `ExtractionHud`：倒计时、撤离进度和紧急提示。

现有 `BattleOutcomeController` 需要支持关卡目标策略，不能继续把“敌方编队为 0”硬编码为所有关卡的胜利条件。推荐引入：

```text
BattleObjectiveType.Elimination
BattleObjectiveType.TimedExtraction
```

`TimedExtraction` 模式下：

- 敌方归零只发送战况事件，不请求胜利。
- `ExtractionObjectiveController` 是胜利和超时失败的唯一目标来源。
- 玩家全灭仍由通用失败逻辑立即处理。
- 最终仍统一调用 `BattleOutcomeController.ResolveOnce`，继续复用冻结模拟、奖励快照和结算 UI，避免出现两个结算入口。

结果快照建议增加：

```text
ObjectiveType
TimeLimitSeconds
RemainingSeconds
RequiredExtractionCount
ExtractedUnitCount
ExtractionCompleted
```

## 6. 视觉与交互规范

- 传送门在战斗开始前可见，但使用关闭状态；开战后播放开启动画。
- 地面增加与 2×2 逻辑撤离区一致的描边，不让玩家靠特效范围猜判定边界。
- 点击传送门等同于点击其撤离区中心，不抢占 UI 点击，也不绕过编队命令层。
- 可撤离玩家单位进入时使用蓝/绿色闪光；敌人进入时不给成功反馈。
- 单位进入流程建议为：停止移动 -> 0.2 秒吸入/缩小 -> 隐藏模型 -> 释放血条和地图占用 -> 标记 `Extracted`。
- 撤离中的单位立即免疫新伤害，防止动画已经进入但被延迟弹道击杀。
- 传送门相机与 RenderTexture 默认不启用；如果后续启用，必须纳入相机数量、RenderTexture 分辨率和低配开关测试。

## 7. 分阶段开发计划

### 阶段 A：资源隔离验证

1. 将 unitypackage 导入独立目录，保留原始 GUID。
2. 在独立验证场景检查 `PortalTunnelStarter`、开关动画、材质、粒子和 Shader。
3. 确认项目渲染管线兼容性；修复材质时只做 Unity 侧兼容配置，不改模型本体。
4. 选定一个只含入口视觉的运行时预制体，关闭不需要的第二相机、物理吸引和原生传送逻辑。

### 阶段 B：格子撤离核心

1. 增加撤离目标配置、PortalSpawnData 和 2×2 撤离区。
2. 增加单位 `Extracting/Extracted` 生命周期和地图占用释放。
3. 让编队点击传送门后整体移动，并让成员依次撤离。
4. 增加自动切换下一支未撤离编队。

### 阶段 C：胜负与倒计时

1. 将胜负控制器改为可配置目标类型。
2. 接入开战倒计时、超时失败、全灭失败和全员撤离胜利。
3. 处理同帧到达与超时的优先级。
4. 扩展结算快照与奖励触发，保证只结算一次。

### 阶段 D：随机地图和工具

1. 将传送门候选点规划接入随机地图生成。
2. 增加全部署区可达性与路径距离校验。
3. 在随机地图工具中显示传送门位置和失败原因。
4. 对每条关卡规则批量验证固定数量种子。

### 阶段 E：UI、表现与验收

1. 完成倒计时、撤离数量、30/10 秒警告。
2. 接入开关、吸入、完成和失败表现。
3. 验证多指挥官、多兵种、单位死亡、战中生产和敌人堵门。
4. 完成性能、分辨率和重复进入关卡测试。

## 8. 验收清单

- 部署阶段不计时，开始战斗后才计时。
- 敌人全部死亡不会直接胜利。
- 所有存活玩家正式单位撤离后只触发一次胜利。
- 超时且仍有未撤离单位时只触发一次失败。
- 玩家全灭立即失败。
- 死亡、撤离和临时召唤物统计互不混淆。
- 已撤离单位不再占格、受伤、被选中或接受命令。
- 多指挥官仍按编队整体控制，未恢复单兵战斗控制。
- 随机地图的传送门不与建筑/部署区重叠，且对所有玩家部署区可达。
- 固定地图种子产生稳定的传送门位置和地图哈希。
- 传送门 Shader、透明排序和动画在当前项目渲染环境中无粉色、黑面或相机异常。
- 低配模式关闭 PortalView 额外相机后，核心传送门视觉和通关判定仍完整工作。

## 9. 当前建议的 MVP 默认值

| 项目 | 默认值 |
| --- | --- |
| 目标类型 | 限时全员撤离 |
| 时间限制 | 180 秒 |
| 撤离区 | 2×2 格 |
| 开门延迟 | 1 秒 |
| 胜利要求 | 全部存活正式玩家单位撤离 |
| 敌军清零 | 不直接胜利 |
| 传送门实时另一侧画面 | 关闭 |
| 超时处理 | 立即失败并冻结模拟 |

这些默认值用于首轮可玩性验证，后续应由关卡配置资产调整，而不是写死在控制器中。
