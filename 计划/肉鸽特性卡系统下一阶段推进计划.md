# 肉鸽特性卡系统下一阶段推进计划

## 1. 当前状态判断

当前肉鸽特性卡系统可以继续推进。

已具备的基础：

- `TraitEffectModels` 已定义结构化效果。
- `TraitCatalog` 已给 9 张初始特性卡补充 `Effects` 和 `Tags`。
- `TraitRuntimeResolver` 已能从玩家进度和出征名单解析装备卡。
- `TraitEffectService` 已接入战斗运行时。
- `UnitSpawner` 已支持 `RuntimeMaxHealth`。
- `UnitCombatController` 已接入攻击力、冷却、减伤和追击移速修正。
- `UnitMovementController` 已接入移动速度修正。
- `TraitShopDirector` 已能根据战斗损失、已有标签和刷新次数影响商店候选。
- `dotnet build Assembly-CSharp.csproj` 已通过。

因此下一阶段不应继续扩大底层机制，而应先把“可验证、可理解、可成体系”补齐。

## 2. 下一阶段目标

目标不是立刻接真实 AI，而是完成一个稳定的肉鸽闭环：

```text
战斗表现
  -> 商店候选倾向
  -> 玩家购买和装备
  -> 下一场战斗特性生效
  -> 玩家能围绕标签凑出流派
```

阶段完成后，玩家应该能明确感受到：

- 装备卡确实改变战斗表现。
- 商店不是纯随机，会轻微补强已有方向。
- 卡牌可以围绕几个流派组合。
- UI 能告诉玩家当前卡的真实效果。
- 系统没有明显卡顿、误报警告或战斗状态残留。

## 3. 第一优先级：补验证与调试入口

### 3.1 增加肉鸽特性调试面板或日志命令

建议先做开发用调试入口，不必做正式 UI。

功能：

```text
显示当前出征指挥官装备的特性。
显示每个 CommanderGroupId 解析出的 RuntimeTraitEffect。
显示当前编队生命比例。
显示各类倍率：
  攻击倍率
  攻击冷却倍率
  移动倍率
  受伤倍率
  最大生命加成
```

落点建议：

```text
mvp/Assets/Scripts/Battle/Traits/TraitDebugReporter.cs
```

验收：

- 进入战斗后能打印每个玩家编队的特性解析结果。
- 低血/高血阈值变化时，Active 状态能看出来。
- 敌方编队不应出现玩家特性效果。

### 3.2 增加最小自动化测试

优先补纯 C# 可测逻辑，不依赖 Unity 场景。

建议测试：

```text
TraitShopDirector.Roll 同种子同上下文结果一致。
高损失时 defense 标签权重提高。
已有同标签 >= 3 时该标签权重下降。
TraitEffectCatalogExtensions.BuildEffectSummary 输出非空且包含真实数值。
```

如果当前测试框架接入成本高，先做 Editor 菜单校验或简单 PlayMode 验证脚本。

验收：

- 修改卡牌标签或权重后能快速发现商店候选异常。
- 不需要每次手动打完整场战斗才能验证 Director。

## 4. 第二优先级：明确卡牌流派体系

当前卡已经有标签，但还没有明确“流派目标”。建议第一版定义 5 个体系。

### 4.1 低血爆发流

标签：

```text
low_health
attack
cooldown
```

玩法：

```text
编队血量越低，输出越高。
高风险高回报，适合坦克或高血量编队。
```

已有卡：

- 勇敢
- 回光反照

下一批补卡建议：

- 临界射击：编队生命低于 35% 时，攻击冷却降低 12%。
- 破釜推进：编队生命低于 35% 时，移动速度提高 10%。

### 4.2 阵地防守流

标签：

```text
defense
formation
idle
```

玩法：

```text
稳定阵地、少移动、提高减伤和持续输出。
```

已有卡：

- 守备
- 坚守
- 纪律

下一批补卡建议：

- 稳固火线：始终减伤 6%，高血时额外减伤。
- 火线校准：生命高于 70% 时攻击冷却降低 10%。

### 4.3 高血机动流

标签：

```text
mobility
high_health
attack
```

玩法：

```text
保持健康状态，通过机动和先手建立优势。
```

已有卡：

- 鼓舞
- 纪律

下一批补卡建议：

- 满编推进：编队生命高于 70% 时攻击力提高 8%。
- 快速转场：编队生命高于 70% 时移动速度提高 12%。

### 4.4 厚血消耗流

标签：

```text
max_health
defense
sustain
```

玩法：

```text
提高最大生命和减伤，容错高，适合新手和长线战斗。
```

已有卡：

- 坚韧
- 谨慎
- 沉着

下一批补卡建议：

- 加固装甲：最大生命提高 8%，所受伤害降低 4%。
- 战地韧性：生命高于 70% 时减伤 10%。

### 4.5 均衡指挥流

标签：

```text
commander
balanced
support
```

玩法：

```text
不追求极端阈值，而是提供稳定小加成，适合混编。
```

下一批补卡建议：

- 稳健指挥：攻击力、移动速度各提高 5%。
- 战术准备：最大生命提高 5%，攻击冷却降低 5%。

## 5. 第三优先级：商店 Director 优化

当前 Director 已经有基础权重。下一步建议做“轻度成型引导”。

### 5.1 根据已有标签补强体系

规则建议：

```text
已有 low_health >= 2：
  attack / cooldown / low_health 权重提高。

已有 defense >= 2：
  defense / max_health / formation 权重提高。

已有 mobility >= 2：
  mobility / high_health / attack 权重提高。

已有标签过散：
  优先给出现次数最高的前两个标签相关卡。
```

注意：

- 不要 100% 锁定某一流派。
- 仍保留 20%-30% 异流派卡，给玩家转向空间。

### 5.2 增加候选去重体验

建议：

```text
同一轮 3 张候选不重复 DefinitionId。
连续两次刷新尽量不出现完全相同的 3 张组合。
如果玩家金币不足，仍可以看到高价值卡，但购买禁用。
```

第一版可以只做同轮去重，跨轮去重后续再加。

### 5.3 增加流派提示

商店或装备区显示一个很轻的提示即可：

```text
当前倾向：低血爆发
已装备标签：attack x2 / low_health x2
推荐补强：cooldown
```

这不是强制构筑，只是帮助玩家理解自己正在凑什么。

## 6. 第四优先级：补充第二批内置卡

在接 AI 之前，建议先把内置卡扩到 18-24 张。

原因：

- 9 张卡太少，商店 Director 很容易重复。
- AI 校验器需要更多合法样本作为参照。
- 玩家很难真正凑出多个体系。

建议数量：

```text
低血爆发：4-5 张
阵地防守：4-5 张
高血机动：4-5 张
厚血消耗：4-5 张
均衡指挥：3-4 张
```

第一批新增卡仍只使用当前 5 种效果和 3 种触发：

```text
ModifyMaxHealth
ModifyAttackPower
ModifyAttackCooldown
ModifyMoveSpeed
ReduceIncomingDamage

Always
WhileGroupHealthBelowPercent
WhileGroupHealthAbovePercent
```

暂不引入持续 Buff、首次受击、阵型完整、停止移动等事件型触发。

## 7. 第五优先级：Mock AI 与校验器

等内置卡池和 Director 稳定后，再做 AI 层。

### 7.1 TraitCardValidator

先做本地校验器，不接真实 AI。

校验内容：

```text
DefinitionId 非空且格式合法。
名称和描述长度合法。
Rarity 合法。
BuyPrice / SellPrice 合法。
Effects 不为空。
EffectKind 在白名单内。
TriggerKind 在白名单内。
Scope 第一版必须是 AllGroupMembers。
Value 在稀有度预算内。
Tags 至少 1 个，最多 4 个。
```

处理：

```text
可修复：Clamp 数值、补默认价格、去掉空 tag。
不可修复：Reject。
```

### 7.2 MockAiTraitCardGenerator

Mock 生成器不调用网络，只返回几组预设 JSON/DTO：

```text
合法卡。
数值超标卡。
非法 Trigger 卡。
缺字段卡。
重复 ID 卡。
```

目标：

- 验证校验器能拦住坏数据。
- 验证商店能混入生成卡。
- 验证 AI 失败时仍回退内置卡池。

### 7.3 暂不接真实 Provider

真实 AI Provider 放到下一阶段。当前重点是把接口、校验和回退跑通。

## 9. 风险控制

| 风险 | 控制 |
| --- | --- |
| 卡池扩张导致平衡失控 | 所有新卡只用当前 5 种效果和 3 种触发 |
| 商店过度引导导致套路固定 | 保留异流派候选概率 |
| UI 文字太多溢出 | 卡面显示摘要，详细解释后续放 Tooltip |
| AI 接入过早导致返工 | 先做 Validator 和 Mock |
| 战斗状态被特性系统污染 | 特性继续保持查询式服务，不主动发移动/攻击命令 |
| 性能问题 | 不在战斗中解析卡定义，不在每帧扫描卡池 |

## 11. 进一步优化与完善点

### 11.1 先补“体系成型判定”，再做正式流派 UI

文档前面已经定义了 5 个流派，但还缺一个统一判定方法。建议新增轻量分析器：

```text
TraitBuildAnalyzer
  输入：玩家当前拥有/装备的卡牌定义
  输出：BuildAffinitySummary
```

建议数据：

```csharp
sealed class BuildAffinitySummary
{
    public string PrimaryArchetypeId;
    public string SecondaryArchetypeId;
    public int PrimaryScore;
    public readonly List<string> RecommendedTags;
    public readonly Dictionary<string, int> TagCounts;
}
```

流派分数第一版用标签计数即可：

```text
低血爆发 = low_health * 2 + attack + cooldown
阵地防守 = defense + formation * 2 + idle
高血机动 = mobility * 2 + high_health + attack
厚血消耗 = max_health * 2 + defense + sustain
均衡指挥 = commander + balanced * 2 + support
```

判定阈值：

```text
PrimaryScore >= 4：显示“正在成型”
PrimaryScore >= 6：显示“流派已成型”
PrimaryScore < 4：显示“构筑未定型”
```

这样商店提示、Director 权重和后续 AI Prompt 都能共用同一套分析结果，避免 UI 和概率逻辑各算各的。

### 11.2 卡牌预算表需要前置

扩充到 18-24 张卡之前，先写一个简单预算表，防止新增卡强度飘。

建议第一版预算：

| 稀有度 | 单效果上限 | 双效果总预算 | 价格区间 | 备注 |
| --- | --- | --- | --- | --- |
| Common | 6%-10% | 10% | 5-6 | 只做稳定小加成 |
| Rare | 10%-16% | 18% | 7-8 | 可带条件触发 |
| Epic | 16%-25% | 28% | 9-11 | 允许更窄触发换高收益 |
| Legendary | 暂不开放 | 暂不开放 | 暂不开放 | 等 AI 校验器稳定后再做 |

触发折算建议：

```text
Always：按 100% 计入预算
WhileGroupHealthAbovePercent：按 75% 计入预算
WhileGroupHealthBelowPercent：按 60% 计入预算
```

例子：

```text
低血攻击 +20%，预算约 20% * 0.60 = 12%，适合 Rare。
始终减伤 +8%，预算约 8%，适合 Common/Rare。
高血移速 +15%，预算约 15% * 0.75 = 11.25%，适合 Rare。
```

现有卡里“回光反照”实际实现是低血攻击 +50%、阈值 15%，应该在 UI 摘要里明确；如果按预算过高，可以保留 Epic，但不建议再叠加第二效果。

### 11.3 调整推荐执行顺序

原计划中的“流派提示”依赖卡池和判定器，建议顺序微调为：

```text
1. TraitDebugReporter / 自检入口
2. TraitShopDirector 测试或自检
3. TraitBuildAnalyzer 成型判定
4. 卡牌预算表固化
5. 扩充第二批内置卡
6. Director 使用 TraitBuildAnalyzer 做补强权重
7. 商店 UI 显示流派提示
8. TraitCardValidator + Mock AI
```

这样每一步都依赖前一步的稳定产物，不会先做 UI 后返工判定逻辑。

### 11.4 现阶段不要做永久 AI 生成卡存档

当前 `PlayerProgressionStore` 仍是内存态，没有真正磁盘存档。下一阶段如果直接做 AI 生成卡定义持久化，会把范围拉大。

建议拆开：

```text
下一阶段：只做内置卡 + Mock AI 候选，不要求跨进程保存 AI 生成定义。
再下一阶段：如果引入真实 AI，再补 GeneratedTraitDefinitionRecord 和磁盘存档。
```

现阶段 Mock AI 的生成卡可以只在同一商店会话内存在：

```text
ShopOffer.DefinitionSnapshot
Session 内购买后转为普通实例
退出进程后不保证恢复
```

这和当前内存进度模型一致，避免为了 AI 提前重写存档系统。

### 11.5 商店刷新需要考虑“已购买候选”

当前商店刷新会替换全部候选。后续如果要强化肉鸽体验，建议保留规则明确化：

```text
刷新会替换所有候选，包括已购买空位。
已购买卡已经进入库存，不会丢失。
刷新前无需补位。
```

UI 上最好区分：

```text
已购买
刷新后替换
库存已有
金币不足
```

这样玩家不会误以为刷新会删除已买卡。

### 11.6 新卡命名和描述要与真实效果一致

当前部分初始卡采用“设计意图描述 + 第一版简化效果摘要”。下一阶段新增卡应直接按真实效果写描述，减少理解成本。

推荐格式：

```text
短描述：编队生命低于 35% 时，攻击冷却降低 12%。
效果摘要：攻击冷却 -12%；编队生命低于 35% 时生效；作用范围：本编队全体。
```

避免：

```text
首次、短时间、阵型完整、停止移动、命中稳定性
```

除非对应触发和系统已经真实实现。

### 11.7 Director 不应该只看“拥有卡”，还要看“装备卡”

当前标签收集包含库存和已装备卡。下一步建议区分两个权重：

```text
EquippedTags：决定当前流派倾向，权重大。
InventoryTags：决定玩家长期库存，权重小。
```

示例：

```text
已装备 low_health x2：强烈补 attack/cooldown。
库存 low_health x2 但没装备：轻微补 low_health，不强推。
```

这样商店更贴近玩家本轮出征构筑，而不是被仓库里的旧卡长期绑架。

### 11.8 给“转流派”留出口

如果 Director 一直强化当前标签，玩家可能被困在早期选择里。

建议每轮 3 张候选使用结构：

```text
1 张：当前主流派补强
1 张：当前次流派或通用卡
1 张：异流派机会卡
```

如果卡池不足，可以退化为加权随机，但目标结构应写进 Director 设计。

### 11.9 补一个“无效构筑保护”

有些卡可能条件相互冲突，例如高血机动和低血爆发混太多，玩家体验会碎。

下一阶段可以先只做提示，不做强限制：

```text
当前构筑条件分散，建议集中补强：low_health 或 defense。
```

不要禁止玩家混搭，因为混搭也可能是策略。

### 11.10 完成标准再收紧一点

建议把完成标准补充为：

- 至少 18 张卡中，每个流派至少 3 张可用卡。
- 每个流派至少有 1 张 Common/Rare 早期可获得卡。
- `TraitBuildAnalyzer` 能给出主流派、次流派和推荐标签。
- 商店 3 张候选中至少 1 张和推荐标签相关，除非卡池不足。
- 新增卡全部有真实效果摘要，且描述不包含未实现触发。
- Director 自检覆盖 3 种上下文：高损失、低损失、标签过散。
