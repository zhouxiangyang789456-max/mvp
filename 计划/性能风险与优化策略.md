# 性能风险与优化策略

## 目标

本项目是 RTS 即时指挥玩法，即使第一版单位数量不多，也要从一开始避免高频寻路、频繁实例化、UI 重建、过多特效、过多碰撞检测等常见性能问题。本文档列出可能导致明显掉帧、卡顿或 GC 峰值的操作，并给出第一版规避策略。

本项目采用“预防优先”的性能策略：第一版开发时就按防卡顿架构实现，不等出现卡顿后再返工。

## 第一版强制性能规则

以下规则第一版必须遵守：

- 寻路必须节流，禁止每帧寻路。
- 特效、血条、选中圈、目标点标记必须对象池。
- UI 文本和血条必须事件驱动或脏标记刷新，禁止每帧全量刷新。
- 地图 tile 不加 Collider。
- 小地图不使用实时 RenderTexture。
- `ReferenceOverlay` 不能进入运行时。
- 高频逻辑禁止 `Debug.Log`。
- 禁止在 `Update()` 中调用 `FindObjectOfType`、`GameObject.Find`、`GetComponentsInChildren`。
- 禁止在移动、攻击、寻路循环里频繁 `new List`、`new Dictionary`。
- 单位模型第一版关闭复杂实时阴影，使用简单阴影或贴地阴影。

## 防卡顿默认架构

### 中央 Tick 调度

不要让所有系统各自在 `Update()` 里做重活。第一版建立轻量调度：

```text
BattleTickService
├── FastTick    每帧：输入、单位平滑移动、摄像机
├── MediumTick  每 0.1s：攻击距离检查、血条朝向
└── SlowTick    每 0.3s - 0.5s：追击重新寻路、小地图点位刷新
```

规则：

- 单位位移可以每帧更新。
- 攻击距离检查不需要每帧对所有单位全量执行。
- 追击寻路必须走 `SlowTick`。
- UI 数值变化通过事件立刻更新，不走全量轮询。

### 对象池默认开启

第一版至少建立这些对象池：

```text
EffectPool
├── MuzzleFlash
├── HitSpark
├── BulletTracer
└── InvalidClickFlash

UiPool
├── UnitHealthBar
├── SelectionRing
├── MoveTargetMarker
└── DeploymentCellHighlight
```

规则：

- 池对象场景加载时预热。
- 播放完成后禁用并归还。
- 池不够时允许扩容，但需要记录警告，方便后续调预算。

### UI 脏标记刷新

UI 控制器使用脏标记：

```text
healthDirty
goldDirty
selectionDirty
tooltipDirty
formationDirty
```

规则：

- 数值变化时标脏。
- `LateUpdate` 或 UI Tick 中只刷新脏对象。
- 不给没变化的 TMP 文本重新赋值。
- 不反复开关整个 Canvas，改局部对象 active 即可。

### 寻路请求队列

第一版单位少，可以同步 A*，但接口要按队列设计：

```text
PathRequestQueue
├── Enqueue(unit, targetGrid, priority)
├── Process(maxRequestsPerFrame)
└── Complete(path)
```

第一版规则：

- 普通移动命令优先级高。
- 攻击追击重新寻路优先级低。
- 每帧最多处理 `1 - 2` 个寻路请求。
- 如果同一单位已有旧请求，新请求覆盖旧请求。
- 目标格不变时不重复入队。

这样即使后续单位数量增加，也不会在同一帧集中卡住。

### 资源预热

进入战斗前或 `BattleBootstrap` 初始化时预热：

- 单位 prefab。
- 地形 tile sprite。
- UI prefab。
- 血条对象池。
- 高亮格对象池，至少 25 个。
- 开火和命中特效对象池。

战斗过程中不从磁盘临时加载资源。

## 高风险性能点

### 频繁寻路

风险：

- 每个单位每帧重新计算 A* 会导致 CPU 飙升。
- 多个单位同时改目标时，如果同步计算路径，容易出现瞬时卡顿。

第一版策略：

- 只在收到新移动命令、攻击目标位置变化超过 `1` 个格子、路径被阻挡时重新寻路。
- 禁止在 `Update()` 中无条件寻路。
- 攻击追击时，每 `0.3s - 0.5s` 最多重新寻路一次。
- 地图第一版较小，但仍使用 `PathRequestQueue` 接口，每帧最多处理 `1 - 2` 个寻路请求。
- 缓存格子邻居，不在寻路时反复分配临时列表。

### 频繁 Instantiate / Destroy

风险：

- 子弹、炮口火光、命中特效、血条、选中圈如果频繁创建销毁，会造成 GC 和卡顿。

第一版策略：

- 单位、血条、选中圈、移动目标标记、攻击特效全部使用对象池，场景初始化时预热。
- 开火特效使用预创建对象，播放完归还池。
- 不在攻击循环里 `Instantiate` 新特效。
- 不在死亡时立刻销毁大量对象，先禁用并回收到池。

### UI 频繁重建

风险：

- 每帧刷新 TextMeshPro 文本、血条布局、卡牌 LayoutGroup，会造成 Canvas rebuild。
- 大 Canvas 上任何元素变动都可能影响整块 UI。

第一版策略：

- 主 UI 和单位血条 UI 分开 Canvas。
- 固定屏幕 UI 使用 `Screen Space - Overlay`。
- 单位血条使用 World Space Canvas 或 Billboard，按单位独立更新。
- 生命值、金币、Tooltip 文本只在数值变化时刷新。
- 不在每帧设置相同的 UI 文本。
- 底部卡槽第一版不使用动态 LayoutGroup 每帧重排，位置固定。
- 阵型按钮高亮只在阵型变化时更新。
- 部署范围高亮进入模式时创建/启用，退出模式时回收/禁用，不每帧重建。

### 过多透明叠加和大图

风险：

- 大面积半透明 UI、部署范围高亮、地形透明覆盖会提高 overdraw。
- 参考图如果误留在运行时，会额外绘制一整屏大图。

第一版策略：

- `ReferenceOverlay` 必须 Editor Only 或运行时关闭。
- 部署范围最多显示 `5x5`，不要整图铺半透明遮罩。
- 高亮格使用合批友好的简单材质。
- 大背景图控制分辨率和压缩格式。
- 小地图第一版使用静态压缩图，不实时渲染 RenderTexture。
- 战斗 UI 装饰图尽量打图集，减少 draw call。

### 3D 单位模型过重

风险：

- 步兵如果每个小队有 12 个士兵，每个士兵高面数、复杂骨骼，会很快吃掉 CPU/GPU。
- 坦克如果材质过多、网格过细、实时阴影复杂，也会掉帧。

第一版策略：

- 步兵小队总面数控制在低模范围，优先 6 人小队，最多 12 人。
- 第一版步兵动画用简单循环，避免复杂骨骼。
- 坦克车体、炮塔、炮口分离即可，不做复杂内部结构。
- 共享材质，减少材质数量。
- 第一版关闭复杂实时阴影，使用简单投影或 blob shadow。
- 远距离单位可降低动画更新频率，第二阶段再做 LOD。
- 同类型单位使用同一材质实例，阵营色优先通过材质属性块或少量共享材质处理。

### 物理碰撞过度使用

风险：

- 给每个单位、每个 tile、每个高亮格都加复杂 Collider，会导致物理检测成本上升。
- 用 Physics Raycast 检测所有 UI/地形/单位混在一起，容易复杂。

第一版策略：

- 地图点击优先使用数学转换：屏幕点 -> 世界点 -> `WorldToGrid`。
- 单位点击使用简单 Collider 或 Physics Raycast，只检测 UnitLayer。
- Tile 不给每格加 Collider。
- 高亮格不加 Collider，点击仍通过格子坐标判断。
- 碰撞只做逻辑占格，不做复杂物理挤压。
- Raycast 使用 LayerMask，避免打到 UI、地形装饰和无关对象。

### 小地图实时渲染

风险：

- 用第二摄像机实时渲染小地图会增加一次场景渲染。
- 如果小地图每帧刷新大量单位点，也会增加 UI 成本。

第一版策略：

- 小地图使用静态图片。
- 单位点第一版可不做，或只用少量 Image 标记。
- 点击小地图只计算摄像机定位，不做实时 RenderTexture。
- 第二阶段再考虑真实同步小地图。
- 如果第一版显示单位点，只在单位跨格或 SlowTick 时更新位置。

### 频繁日志输出

风险：

- Unity `Debug.Log` 在 Update、寻路、攻击循环里大量输出会显著卡顿。

第一版策略：

- 高频逻辑禁止 `Debug.Log`。
- 只在命令下达、错误、状态切换调试时输出。
- 调试日志使用开关控制。
- 发布/验收时关闭调试日志开关。

### 资源加载时卡顿

风险：

- 进入战斗时同步加载大量贴图、模型、动画，会出现明显卡顿。

第一版策略：

- 第一版资源数量较少，可以随场景加载。
- 后续资源增加后，需要进入战斗前预加载。
- 单位 prefab、地形 sprite、UI prefab 在 `BattleBootstrap` 初始化阶段统一准备。
- 战斗过程中不临时从磁盘加载资源。

## 卡顿应急处理顺序

如果测试中出现卡顿，按这个顺序排查：

1. Unity Profiler 查看是否有 GC Alloc。
2. 检查是否有每帧寻路。
3. 检查是否有 Instantiate / Destroy 峰值。
4. 检查 Canvas rebuild 是否过高。
5. 检查 Debug.Log 是否高频输出。
6. 检查小地图是否误用 RenderTexture。
7. 检查单位模型面数、材质数量和阴影。
8. 检查 Physics Raycast 是否没有 LayerMask。

## 第一版性能预算

建议目标：

```text
目标分辨率: 1600x900 / 1920x1080
目标帧率: 60 FPS
己方单位: 3
敌方单位: 1 - 3
地图尺寸: 12 x 10
部署高亮: 最多 25 格
同时特效: 少于 20 个
主 Canvas: 1 个
单位 World Space Canvas: 每单位 1 个或共享 Billboard 管理器
```

虽然第一版规模小，但代码结构要按后续扩展考虑。

## 需要避免的写法

```text
不要每帧 A*。
不要每帧刷新所有 UI 文本。
不要每帧 Instantiate / Destroy 特效。
不要给每个 tile 加 Collider。
不要让参考图在运行时显示。
不要使用实时 RenderTexture 小地图。
不要在 Update 中 FindObjectOfType / GameObject.Find。
不要给所有单位使用复杂实时阴影。
不要在循环中频繁 new List / new Dictionary。
不要在高频逻辑里 Debug.Log。
```

## 推荐实现习惯

- 输入处理集中在 `BattleInputController`。
- 命令下发集中在 `UnitCommandController`。
- 寻路集中在 `PathfindingService`。
- UI 刷新使用事件或脏标记。
- 特效使用 `EffectPool`。
- 单位血条使用 `UnitHealthBarManager` 管理。
- 地图格数据使用数组，不用频繁字典查询。
- 单位状态切换只在状态变化时触发动画切换。

## 性能验收标准

第一版验收时检查：

- 空场景战斗页稳定运行，无明显卡顿。
- 连续点击移动命令不会卡顿。
- 单位攻击循环不会产生持续 GC。
- 反复进入/退出阵型部署模式不会产生大量对象。
- UI 文本变化不会引发明显帧率下降。
- Unity Profiler 中没有每帧大量 GC Alloc。
- `ReferenceOverlay` 不在运行时显示。
- 小地图没有使用实时摄像机渲染。

## 后续扩展优化

第二阶段或单位数量增加后再考虑：

- 寻路分帧队列。
- 群体移动避让。
- 单位 LOD。
- 动画更新降频。
- GPU Instancing。
- 地形 chunk 合批。
- Addressables 预加载。
- 小地图增量刷新。
- ECS 或 Job System。
