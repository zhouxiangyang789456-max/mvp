# 战斗胜负判定与结算流程方案

## 1. 目标与当前缺口

当前单位生命归零后，`UnitCombatController` 会将单位设为 `Dead`，随后 `UnitView.Die()` 从 `CommanderGroupRegistry` 移除成员。编队成员清空后虽然会进入 `Defeated`，但项目缺少统一的战斗裁决器，因此敌人全部被消灭后不会产生胜利结果，也不会弹出结算页面。

本方案补齐以下闭环：

```text
单位死亡
-> 编队失败
-> 阵营存活状态变化
-> 胜负候选
-> 延迟确认
-> 锁定战斗
-> 结果弹窗
-> 胜利进入结算商店 / 失败重试或返回
```

胜负系统只负责裁决和流程衔接，不直接修改攻击、寻路、阵型和 AI 决策实现。

## 2. MVP 胜负规则

### 2.1 胜利

满足以下全部条件时判定玩家胜利：

1. 战斗已经正式进入 `Combat` 阶段。
2. 玩家和敌方初始编队均已完成注册。
3. 至少生成过一个有效敌方编队。
4. 所有敌方编队均为 `Defeated`，即不存在存活敌方成员。
5. 玩家至少仍有一个未失败编队。
6. 候选结果经过一个短裁决窗口后仍然成立。

胜利不能仅依赖场景中找不到红色模型，因为死亡对象使用延迟销毁，视觉对象和逻辑状态可能短暂不同。唯一权威来源是编队注册表中的运行时成员状态。

### 2.2 失败

满足以下全部条件时判定玩家失败：

1. 战斗已经进入 `Combat` 阶段。
2. 初始双方编队注册已经完成。
3. 所有玩家编队均为 `Defeated`。
4. 敌方至少仍有一个未失败编队。
5. 候选结果经过裁决窗口后仍然成立。

失败后不进入商店，也不发放通关金币。结果弹窗提供“重新挑战”和“返回”入口。

### 2.3 同归于尽

若同一裁决窗口内玩家和敌方都不存在存活编队，结果为 `Draw`：

- 不按代码执行先后把它算成胜利或失败。
- 不发放胜利奖励，不进入商店。
- 弹窗显示“双方全灭”，提供重新挑战和返回。

MVP 不加入超时、占点、护送、撤退等额外胜负条件。这些条件后续通过独立 `IBattleObjective` 扩展，不能散落在 UI 或单位代码中。

## 3. 启用门禁

胜负检测必须经过显式启用，避免加载和部署期间因为敌人尚未生成而误判胜利。

```text
Uninitialized
-> Registering       创建网格、服务并生成双方编队
-> Armed             双方注册完成，但仍处于部署阶段
-> Running           玩家点击“开始战斗”
-> Candidate         收到可能结束战斗的状态变化
-> Resolved          结果只写入一次
-> Presenting        显示结果弹窗
-> Transitioning     重试、返回或进入商店
```

进入 `Running` 的必要条件：

- `BattlePhaseState.Current == Combat`。
- `UnitSpawner` 已明确调用 `NotifyInitialSpawnCompleted()`。
- 初始玩家编队数大于 0。
- 初始敌方编队数大于 0。
- 核心服务无启动错误。

若任一条件不满足，只输出一次明确错误并保持未启用，不能把缺少敌人当作胜利。

## 4. 权威数据与失败事件

### 4.1 编队注册表事件

扩展 `CommanderGroupRegistry`：

```csharp
event Action<CommanderGroupRuntime> GroupRegistered;
event Action<CommanderGroupRuntime> GroupDefeated;
event Action<CommanderGroupRuntime> GroupRemoved;
```

`NotifyUnitRemoved()` 在编队第一次从“存在存活成员”转为“无存活成员”时：

1. 将状态设为 `Defeated`。
2. 停止编队命令和 AI。
3. 清理选择、视野、路径与阵型预留。
4. 发出一次 `GroupDefeated`。

必须增加单次通知保护，例如 `DefeatNotified`。重复销毁、`OnDestroy` 和场景卸载不得重复发出失败事件。

### 4.2 不删除编队记录

失败后成员可以从 `Members` 移除，但本局内编队运行记录应保留到战斗结束，以便：

- 统计初始和失败编队数量。
- 生成结算战报。
- 区分“从未生成”与“已经全灭”。
- 防止对象销毁后阵营历史丢失。

### 4.3 存活定义

编队存活必须满足：

```text
Members 中至少有一个非空成员
且成员 Data 非空
且 State != Dead
且 CurrentHealth > 0
```

生命值与状态出现矛盾时，`CurrentHealth <= 0` 优先视为死亡并记录诊断信息。裁决器不能依赖 GameObject 是否已经 `Destroy`。

## 5. 战斗结果裁决器

新增 `BattleOutcomeController`，挂载到 `BattleCore`，成为唯一允许写入最终结果的组件。

### 5.1 结果模型

```csharp
enum BattleOutcome
{
    None,
    Victory,
    Defeat,
    Draw,
    Aborted
}

sealed class BattleResultSnapshot
{
    string BattleId;
    string LevelId;
    BattleOutcome Outcome;
    int ResolutionTick;
    int InitialPlayerGroups;
    int InitialEnemyGroups;
    int SurvivingPlayerGroups;
    int SurvivingEnemyGroups;
    int PlayerUnitsLost;
    int EnemyUnitsDefeated;
    int RewardGold;
    string RewardGrantId;
    int ShopRandomSeed;
}
```

结果快照一经 `Resolved` 不可修改。UI、奖励和商店全部读取同一快照，不能各自重新统计。

### 5.2 事件驱动检测

正常路径只在以下事件发生时检查：

- 初始生成完成。
- 进入 `Combat`。
- `GroupDefeated`。
- 后续目标系统报告目标状态改变。

不在 `Update()` 中每帧扫描单位。为了抵抗遗漏事件，可在 `BattleTickService` 的低频 Tick 中每 `0.5` 秒进行一次编队级一致性核对；只扫描编队，不扫描场景 GameObject。

### 5.3 裁决窗口

第一次发现胜利、失败或平局候选时进入 `Candidate`，默认等待 `0.35` 秒或固定数量 Slow Tick：

- 窗口内只记录阵营状态变化，不立刻弹窗。
- 到期后重新读取双方存活编队数。
- 结果改变则更新候选或取消候选。
- 结果稳定才调用 `ResolveOnce()`。

这样可以处理同一帧多发攻击、投射物延迟、多个单位连续死亡和同归于尽。

### 5.4 幂等解决

`ResolveOnce()` 必须使用状态门禁：

```csharp
if (_state >= BattleOutcomeState.Resolved) return false;
```

只允许第一次调用：

- 写入 `BattleResultSnapshot`。
- 冻结战斗模拟。
- 发出 `BattleResolved`。
- 创建结果 UI。

重复事件、场景卸载和按钮连点不得重复发奖、重复打开商店或重复加载场景。

## 6. 结束战斗时的冻结顺序

结果确认后按以下顺序执行：

1. 将结果状态写为 `Resolved`，阻断二次裁决。
2. 禁止玩家下达移动、攻击和重整命令。
3. 停止敌方 AI 新决策。
4. 取消或失效化正在排队的寻路请求。
5. 停止单位造成新伤害，但允许当前帧表现结束。
6. 清除选择高亮和指挥官检查面板。
7. 隐藏普通战斗 HUD，保留背景战场。
8. 在短暂停顿后显示结果弹窗。

不建议直接设置全局 `Time.timeScale = 0`，因为这会影响 UI 动画和异步过渡。应使用 `BattleSimulationState.IsFrozen` 或让 Tick 服务暂停战斗 Tick，而 UI 继续使用非缩放时间。

## 7. 结果弹窗

新增 `BattleResultController` 与 `BattleResultView`。弹窗覆盖战斗画面并使用暗色遮罩。

### 7.1 胜利弹窗

显示：

- “胜利”。
- 消灭敌方单位数。
- 我方损失和存活编队数。
- 本关获得金币。
- “进入商店”按钮。

点击“进入商店”后构造：

```csharp
new SettlementShopOpenArgs
{
    SessionId = result.BattleId + "_shop",
    RewardGrantId = result.RewardGrantId,
    RandomSeed = result.ShopRandomSeed,
    RewardGold = result.RewardGold
}
```

然后调用 `SettlementShopController.OpenShop(args)`。结果页只负责传递快照，不直接写玩家金币；金币由商店会话按 `RewardGrantId` 幂等处理。

### 7.2 失败与平局弹窗

显示结果、损失和两个按钮：

- “重新挑战”：清理当前战斗运行状态并重新加载本关，不发奖励。
- “返回”：回到指挥官选择页或上一级流程，不发奖励。

失败和平局不创建 `SettlementShopOpenArgs`。

### 7.3 输入锁

结果弹窗出现后：

- 只接受弹窗按钮输入。
- 禁止点击地图、单位和指挥官头像。
- 按钮提交后立即禁用，直到场景过渡完成。
- 场景过渡失败时恢复按钮并显示错误，不能留在不可操作状态。

## 8. 奖励与商店幂等

奖励不能在“检测到胜利”“弹窗出现”和“进入商店”三个位置分别记账。

推荐规则：

- 胜利裁决只生成奖励快照，不修改永久金币。
- 打开商店会话时将奖励加入金币草稿。
- 商店最终确认后与购买、出售、装备结果一起提交。
- `RewardGrantId` 在永久进度中记录已领取状态。
- 同一 `BattleId`、`SessionId` 或 `RewardGrantId` 重复执行只返回既有结果。

如果玩家在胜利弹窗退出应用，恢复后应重新显示同一结果或同一商店会话，不重新随机奖励和候选卡。

## 9. 生命周期与重试

### 9.1 开始新战斗

必须重置：

- 上一局 `BattleOutcome` 和候选计时。
- 初始编队计数和统计。
- 输入锁与模拟冻结状态。
- 上一局结果弹窗实例。
- 未完成寻路、AI 记忆、选择和战斗事件订阅。

### 9.2 场景退出

销毁顺序：

1. 结果控制器停止接收事件。
2. 战斗服务停止 Tick。
3. 取消异步请求。
4. 清理单位和编队。
5. `BattleCore.Teardown()`。

卸载过程中发生的 `OnDestroy -> NotifyUnitRemoved` 不得触发失败弹窗，因此裁决器进入 `Aborted` 后忽略所有死亡事件。

## 10. 性能与执行约束

- 单位死亡热路径只做 O(1) 的成员移除和一次编队事件。
- 正常胜负检查复杂度为 O(编队数)，不扫描全部单位或场景对象。
- 低频自愈核对默认 0.5 秒一次，仅在 `Running/Candidate` 状态执行。
- 结果快照只创建一次，不在 UI 刷新时重复分配列表和字符串。
- 结果 UI 只实例化一次；按钮回调避免重复注册。
- 日志只记录状态改变、异常不变量和最终结果，不能每 Tick 输出存活数量。
- 商店和结果弹窗不可同时存在；开始创建商店后销毁或隐藏结果弹窗。

## 11. 建议代码结构

```text
Assets/Scripts/Battle/Outcome/
  BattleOutcome.cs
  BattleResultSnapshot.cs
  BattleOutcomeController.cs
  BattleOutcomeConfig.cs

Assets/Scripts/Battle/UI/
  BattleResultController.cs
  BattleResultView.cs
```

现有文件需要的小范围改动：

```text
BattleCore.cs                  注册 BattleOutcomeController
CommanderGroupRegistry.cs      增加注册和失败事件、单次失败通知
CommanderGroupRuntime.cs       增加 DefeatNotified 与存活统计接口
UnitSpawner.cs                 生成完双方后通知 InitialSpawnCompleted
BattleUiController.cs          开始战斗时通知裁决器进入 Running
BattleTickService.cs           提供冻结模拟和低频核对入口
UnitCombatController.cs        冻结后不再结算伤害
SettlementShopController.cs    接收胜利结果构造的商店参数
```

## 12. 开发顺序

### 阶段 1：权威失败事件

1. 为编队增加稳定的存活统计和 `DefeatNotified`。
2. 为注册表增加 `GroupRegistered`、`GroupDefeated` 事件。
3. 保证最后一个成员死亡时只发一次编队失败事件。
4. 修正销毁、场景退出和重复移除路径。

### 阶段 2：胜负裁决器

1. 增加状态机、启用门禁和初始生成完成通知。
2. 实现事件驱动检查与 0.35 秒裁决窗口。
3. 实现胜利、失败、平局及 `ResolveOnce()`。
4. 增加 0.5 秒低频一致性核对。

### 阶段 3：模拟冻结与输入锁

1. 阻止玩家新命令和 AI 新决策。
2. 停止伤害、移动和路径提交。
3. 清理选择与普通战斗 HUD。
4. 验证 UI 仍可使用非缩放时间响应。

### 阶段 4：结果弹窗

1. 实现胜利、失败和平局状态。
2. 显示基础战报和奖励。
3. 实现按钮防重复提交。
4. 实现重新挑战和返回流程。

### 阶段 5：商店衔接

1. 从结果快照构造稳定的商店参数。
2. 胜利按钮打开结算商店。
3. 保证奖励只在商店最终提交时进入永久进度。
4. 验证重复点击、重开页面和恢复会话不会重复发奖。

## 13. 验收清单

### 基础结果

1. 战斗部署期间敌人尚未生成时不弹胜利。
2. 消灭一个敌方编队但仍有其他敌方编队时不结束。
3. 消灭最后一个敌方编队后约 0.35 秒只弹一次胜利。
4. 玩家最后一个编队全灭后只弹一次失败。
5. 同一裁决窗口双方全灭时显示平局。
6. 已失败编队不再被 AI 或选择系统操作。

### 流程与奖励

1. 胜利弹窗进入商店后奖励金币只出现一次。
2. 失败和平局不能进入商店，也不增加金币。
3. 连续点击“进入商店”不会创建多个商店和多个会话。
4. 商店提交失败时保留草稿，不能重复领取胜利奖励。
5. 重新挑战后上一局结果、冻结状态和事件订阅全部清除。

### 边界情况

1. 多个单位同帧死亡不会重复裁决。
2. `Destroy` 延迟一帧不会阻止胜利。
3. 场景卸载引起的单位销毁不会弹失败。
4. 初始敌方生成失败时报告启动错误，不算胜利。
5. 低频核对发现漏掉的失败事件时能够修正结果。
6. 战斗结束后投射物或旧攻击回调不能继续造成伤害。

### 性能门槛

- 战斗进行时不进行每帧全单位胜负扫描。
- 同时存在多支编队时，胜负检查耗时只随编队数线性增长。
- 结果弹窗显示前后无持续日志、事件订阅或寻路队列增长。
- 编译必须保持 0 错误、0 警告。

## 14. 本轮推荐实现范围

下一轮开发优先完成：

1. 编队失败事件与单次通知。
2. `BattleOutcomeController` 及启用门禁。
3. 胜利、失败和平局裁决。
4. 模拟冻结和输入锁。
5. 基础结果弹窗。
6. 胜利结果连接现有 `SettlementShopController.OpenShop()`。

战报动画、星级评价、额外目标、掉落展示和高级结算美术放在闭环稳定后处理。
