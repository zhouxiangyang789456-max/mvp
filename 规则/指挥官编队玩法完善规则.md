# 指挥官编队玩法完善规则

## 1. 文档定位

本文件是《指挥大师》指挥官选择与战斗编队系统的实现规格，不只是玩法方向说明。

涉及以下内容的开发、重构和验收必须遵守本文件：

- 指挥官选择、出征名单和跨场景数据。
- 战斗中的指挥官切换、点击路由和选中反馈。
- 指挥官编队的部署、移动、攻击、停止、重整和失败状态。
- 单位归属、阵型槽位、寻路、目标分配、死亡注销和 UI 数据绑定。

核心规则只有一句：**选择页面可以选择多名指挥官组成出征队伍；战斗中默认一次激活一名指挥官，所有玩家命令由该指挥官编队整体执行。**

## 2. 当前实现与目标实现

### 2.1 当前实现

当前项目仍包含以下单人、单兵逻辑：

| 当前位置 | 当前行为 | 必须改成 |
| --- | --- | --- |
| `BattleStartContext.SelectedCommander` | 只传递一名指挥官 | 传递有顺序的出征名单快照 |
| `CommanderSelectController._selected` | 只保存一个卡片索引 | 区分当前查看对象和已选出征名单 |
| `UnitSpawner` | 只生成一名指挥官的初始单位 | 按出征名单生成多个独立编队 |
| `UnitRuntimeData` | 没有指挥官归属 | 增加稳定的 `CommanderGroupId` |
| `UnitSelectionController.Selected` | 直接选中单个士兵 | 选中士兵时解析并激活其所属编队 |
| `UnitMovementController.CommandMove(UnitView, ...)` | 玩家命令直接发给单兵 | 只作为编队内部执行器使用 |
| `UnitCombatController.CommandAttack(UnitView, ...)` | 玩家命令直接发给单兵 | 只作为编队内部执行器使用 |
| `FormationController` | 收集所有玩家单位形成一个阵型 | 只处理当前指挥官编队及其独立阵型 |
| `BattleUiController` | 只显示一名指挥官 | 显示出征名单并绑定当前激活编队 |

### 2.2 目标调用链

```text
选择页面卡片
  -> 出征名单 ExpeditionRosterSnapshot
  -> BattleStartContext
  -> 为每名指挥官创建 CommanderGroupRuntime
  -> 战斗中激活一个 CommanderGroupRuntime
  -> 玩家发出 GroupCommand
  -> 编队计算锚点、阵型槽位和目标分配
  -> 单位移动/攻击控制器执行分配结果
```

任何玩家输入都不得绕过 `CommanderGroupRuntime` 或编队命令层直接控制某个士兵。

## 3. 术语与唯一标识

### 3.1 指挥官定义

`CommanderDefinition` 是静态配置，至少包含：

- `Id`：全项目唯一且稳定，例如 `commander_elena`。
- `DisplayName`、`MaxHealth`、特性和初始单位配置。
- `MapPortraitAssetId`：地图指挥标记使用的透明头像资源 ID。
- 默认阵型、指挥官战斗参数和美术资源引用可以后续加入。

静态定义不得保存一场战斗中的可变成员列表、当前命令或临时位置。

### 3.2 出征名单

`ExpeditionRosterSnapshot` 是从选择页面传入战斗的只读快照，必须保持玩家选择顺序。

每一项至少包含：

```csharp
CommanderId
RosterIndex
StartingHealth
StartingUnitsSnapshot
InitialFormation
```

不得把场景对象、`MonoBehaviour`、按钮引用或可变的 `CommanderDefinition` 实例直接当作跨场景存档。

### 3.3 指挥官编队

`CommanderGroupRuntime` 表示一名指挥官及其麾下全部单位，至少维护：

```csharp
GroupId                 // 本场战斗唯一
CommanderId             // 静态定义 ID
RosterIndex             // 出征顺序
Team
CommanderView           // 指挥官世界对象；尚无模型时允许为空
MapMarker               // 地图上的指挥官头像标记，玩家编队必须存在
Members                  // 全部成员
AliveMembers             // 可执行命令的成员
AnchorCell               // 编队逻辑锚点
Facing                   // 编队朝向
Formation                // 当前阵型
State                    // 编队状态
CurrentCommand           // 当前编队命令
CommandSequence          // 单调递增命令序号
```

`GroupId` 推荐格式为 `group_{team}_{rosterIndex}_{commanderId}`，不能使用显示名称。

### 3.4 单位归属

`UnitRuntimeData` 必须增加：

```csharp
string CommanderGroupId;
int FormationSlotIndex;
int SpawnOrder;
```

单位生成后到死亡注销前，`CommanderGroupId` 不得为空，也不得随 UI 选择变化。

### 3.5 地图指挥标记

`CommanderMapMarker` 是地图内用于显示、识别和点击指挥官的头像对象，与 `CommanderGroupRuntime` 一一对应。

它必须满足：

- 标记代表指挥官编队，不代表某个普通士兵。
- 没有指挥官 3D 模型时，标记跟随编队逻辑锚点。
- 有指挥官 3D 模型后，标记悬浮在 `CommanderView` 上方，但编队选择语义不变。
- 玩家方每个未失败的指挥官编队必须有且只有一个标记。
- MVP 强制显示玩家方指挥官头像；敌方只有在其同样拥有指挥官编队时才显示头像，普通敌军单位不得生成指挥官头像。
- 标记保存稳定的 `GroupId`，点击时通过该 ID 激活编队。
- 标记不能保存或推断单位列表，成员关系仍由编队运行时数据维护。

## 4. 选择页面的具体交互

### 4.1 两种状态必须分开

选择页面必须同时维护：

- `FocusedCommanderId`：当前详情面板正在查看的指挥官，可以为空。
- `SelectedCommanderIds`：已加入出征名单的有序集合，可以包含多名指挥官。

不得再用一个 `_selected` 索引同时承担详情查看和出征名单两个职责。

### 4.2 卡片点击规则

在当前没有独立“加入”按钮的 UI 下，卡片采用以下规则：

1. 点击未加入名单的可用卡片：设为详情焦点，并追加到出征名单末尾。
2. 点击已经加入名单的卡片：保持其为详情焦点，同时从出征名单移除。
3. 移除中间项后，其后成员的 `RosterIndex` 连续前移。
4. 待解锁、无有效 `CommanderId` 或数据校验失败的卡片不可加入。
5. 名单达到上限时，点击其他未选卡片只切换详情焦点，并显示“出征人数已满”，不得静默替换已有成员。

如果以后增加独立复选框或“加入出征”按钮，可以调整第 1、2 条交互，但 `FocusedCommanderId` 与名单仍必须分离。

### 4.3 人数与顺序

- 当前页面有 6 个指挥官卡位；在独立配置建立前，MVP 出征上限沿用 6。
- 建立配置后使用唯一字段 `MaxExpeditionCommanders`，UI、校验和战斗生成都读取同一字段。
- 选择顺序决定战斗初始排序、默认激活对象和部署区域分配顺序。
- 同一 `CommanderId` 在名单中只能出现一次。

### 4.4 卡片视觉状态

每张卡必须只处于下列一种状态：

| 状态 | 表现 | 是否可点击 |
| --- | --- | --- |
| `Locked` | 降低透明度，显示待解锁 | 否 |
| `Available` | 正常边框 | 是 |
| `Focused` | 详情焦点描边 | 是 |
| `Selected` | 明确勾选和出征序号 | 是 |
| `FocusedSelected` | 同时显示焦点和出征序号 | 是 |

只改变轻微色调不足以表达多选；已选卡片必须显示 `1..N` 的出征序号或明确勾选标记。

### 4.5 出征按钮校验

出征按钮仅在以下条件全部满足时可用：

```text
SelectedCommanderIds.Count >= 1
SelectedCommanderIds.Count <= MaxExpeditionCommanders
所有 ID 唯一
所有 ID 能在 CommanderCatalog 中解析
每名指挥官至少有有效生命值和合法初始单位数量
目标战斗场景可加载
```

点击出征时先构造快照，再一次性写入 `BattleStartContext`，最后加载场景。验证失败不得部分写入上下文。

## 5. 跨场景上下文

### 5.1 必须替换的字段

将：

```csharp
BattleStartContext.SelectedCommander
```

替换为类似：

```csharp
BattleStartContext.ExpeditionRoster
```

`ExpeditionRoster` 至少提供：

```csharp
IReadOnlyList<ExpeditionCommanderEntry> Commanders
bool IsValid
void Clear()
```

### 5.2 生命周期

1. 选择页面确认出征时创建快照。
2. 战斗场景读取一次并创建运行时编队。
3. 战斗运行时不得修改选择页面保存的快照。
4. 返回选择页面时可以保留名单；重新开始、完成战斗或明确取消时才调用 `Clear()`。
5. 直接从编辑器打开 `BattleScene` 时，允许用 `CommanderCatalog` 第一名创建单编队调试快照，但必须打印一次明确的 fallback 日志。

## 6. 战斗生成与部署

### 6.1 生成顺序

`UnitSpawner` 必须按 `RosterIndex` 依次执行：

1. 解析 `CommanderDefinition`。
2. 创建 `CommanderGroupRuntime`。
3. 分配不与其他编队重叠的初始 `AnchorCell`。
4. 创建指挥官世界对象或逻辑锚点。
5. 创建并绑定 `CommanderMapMarker`。
6. 根据 `StartingUnitsSnapshot` 生成单位。
7. 为每个单位写入 `CommanderGroupId`、`SpawnOrder` 和 `FormationSlotIndex`。
8. 全部生成成功后注册编队；失败时回滚头像标记、已生成单位和占用格。

不得使用当前 `PlayerCells[idx % PlayerCells.Length]` 的循环覆盖方式生成多编队。

### 6.2 初始区域分配

- 每个编队拥有独立部署区域，区域之间不得共享可放置格。
- 区域按 `RosterIndex` 稳定分配，不能依赖场景对象遍历顺序。
- 某编队空间不足时，先搜索最近的完整合法区域；找不到时拒绝开始战斗并报告具体指挥官 ID。
- 生成前必须批量验证全部目标格，验证通过后再批量占用，避免生成一半后留下脏占用。

### 6.3 部署阶段

#### 6.3.1 3×3 自定义布阵

- 每位玩家指挥官拥有一套独立的 3×3 布阵槽位，槽位编号固定为 `0-8`。
- 点击指挥官地图头像只打开该编队上下文；点击旗下具体单位或单位卡后才进入单位待部署状态。
- 选中单位后点击空槽，单位移动到该槽；点击同编队已占用槽，两个单位交换槽位。
- 点击原槽不产生变化；点击 3×3 外、不可行走格、敌方或其他编队占用格时拒绝操作。
- 竖向、横向、方形按钮是 3×3 的快捷预设。应用后仍可逐格调整，第一次手调后阵型类型记为 `Custom`。
- 切换指挥官时分别恢复其锚点、槽位分配、单位卡和阵型高亮，不得覆盖上一位指挥官的布局。
- 3×3 最多容纳 9 个存活单位。开战前必须校验槽位范围、重复占位、空编队和容量上限。
- 战斗开始后逐格编辑关闭，自定义布局写入阵型快照；移动和攻击只平移锚点，不重新分配槽位。

#### 6.3.2 战斗中主动重整

- 战斗中只有处于 `Idle`、无单位移动且无单位交战的指挥官编队可以进入阵型编辑。
- 编辑使用临时 `单位ID → 3×3槽位` 草稿；预设、空槽移动和占用槽交换都不得立即修改正式阵型或单位位置。
- 点击确认后，系统一次性校验所有目标格、重复槽位和全员路径；任一失败则整次重整拒绝并保留草稿。
- 校验通过后编队进入 `Regrouping`，所有单位通过实际移动抵达新槽位，不允许瞬移或部分提交。
- 点击取消、右键、切换指挥官或关闭指挥官面板时丢弃草稿，正式阵型保持不变。
- 编辑过程中点击敌人或普通战场地面不得触发攻击、移动命令。
- 纯预设编辑确认后保留对应预设类型；发生手动换位后阵型类型记为 `Custom`。
- 重整完成后编队回到 `Idle`；攻击全部结束后也必须回到 `Idle`，之后才允许再次编辑阵型。

#### 6.3.3 单位目标虚影与槽位归属

仅用绿色闪烁格不足以表达多个单位分别要去哪里。部署和战斗重整的目标预览必须支持“单位目标虚影”：

- 每个待部署或待重整单位在自己的草稿目标槽显示一个虚影，虚影与单位实例 ID 一一对应。
- 虚影优先复用该单位当前模型、Sprite 或头像轮廓，并使用半透明材质；不得复制完整运行时单位逻辑、碰撞、血条或选择组件。
- 当前选中单位的本体、单位卡、原槽和目标虚影必须使用同一种强调色或描边，其他单位虚影降低亮度。
- 鼠标悬停目标格时，应高亮对应虚影及其来源单位；悬停或选择来源单位时，应反向高亮目标格。
- 手动交换两个槽位时，两份虚影同时更新，不得让玩家误以为只有一个单位发生变化。
- 空槽只显示普通可部署格，不显示虚影；非法槽使用红色或禁止标记，不复用绿色确认反馈。
- 编辑草稿期间虚影跟随草稿槽位；取消时全部隐藏；确认后虚影保持到实际单位开始移动或短暂淡出。
- 虚影仅用于表达计划位置，不参与射线命中、寻路、占用、视野、AI 感知和战斗判定。

当前没有正式单位美术资源时允许分阶段回退：

1. 第一回退：使用与单位类型一致的半透明占位几何体，并在虚影上方显示单位类型或序号。
2. 第二回退：使用单位头像小圆标或兵种图标放在目标格中心。
3. 最低回退：目标格显示稳定编号，并在单位卡和单位本体旁显示相同编号。

即使暂缓制作虚影资源，也必须预留 `UnitId -> PreviewObject` 的数据与生命周期接口，不能继续只保存无归属的绿色格列表。

- 默认激活 `RosterIndex == 0` 的指挥官。
- 玩家切换指挥官后，部署范围、阵型预览和底部单位卡切换到对应编队。
- `FormationController` 的所有入口必须接收或解析当前 `CommanderGroupRuntime`。
- `ApplyFormation`、`CountPlayerUnits` 和 `ComputeAnchor` 只能遍历当前编队成员，禁止继续遍历全部 `TeamId.Player` 单位。
- 部署阶段允许调整当前编队整体阵型；是否允许手工交换单个槽位是独立功能，不能恢复单兵战斗控制。

## 7. 战斗中的选择与输入路由

### 7.1 默认单激活规则

- 一次只允许一个 `ActiveCommanderGroupId`。
- 点击己方指挥官，激活其编队。
- 点击地图指挥官头像，直接激活头像绑定的编队，并消费本次地图点击。
- 点击己方普通单位，解析其 `CommanderGroupId` 并激活所属编队。
- 点击战斗 UI 中的指挥官头像，激活对应编队。
- `Esc` 或右键只清除当前操作预览；是否清除激活编队必须统一配置，MVP 默认不清除激活编队。
- 不支持 `Shift` 多选和框选多编队；若以后增加，必须先更新本规则。

### 7.2 左键路由

当前项目沿用左键下令：

| 点击对象 | 条件 | 结果 |
| --- | --- | --- |
| 地图指挥官头像 | 己方且未失败 | 激活其 `GroupId`，本次点击不再下达移动命令 |
| 己方指挥官/单位 | 任意战斗阶段 | 激活其所属编队 |
| 空地 | 部署阶段 | 移动当前编队锚点或放置允许的槽位 |
| 空地 | 战斗阶段 | 发出 `Move` 编队命令 |
| 敌方指挥官/单位 | 战斗阶段 | 解析敌方所属编队并发出 `AttackGroup` 命令 |
| 敌方对象 | 部署阶段 | 忽略并显示不可操作反馈 |
| UI | 任意阶段 | 不向地图透传点击 |

`UnitSelectionController` 可以继续维护格子到单位的拾取注册表，但 `Selected` 必须改为编队选择，不得继续作为玩家命令中的攻击者或移动者。

## 8. 编队命令模型

### 8.1 命令类型

建立独立的 `GroupCommandType`，至少包含：

```csharp
None
Move
AttackGroup
Hold
Regroup
FormationDeploy
```

不要复用 `UnitCommand` 作为玩家级命令。单位命令是编队命令分解后的执行结果。

### 8.2 命令字段

`GroupCommand` 至少包含：

```csharp
long Sequence;
GroupCommandType Type;
Vector2Int TargetAnchorCell;
string TargetGroupId;
string PrimaryTargetUnitId;
FormationType RequestedFormation;
float IssuedAt;
```

每次接受新命令时递增 `Sequence`。异步寻路或延迟回调应用结果前必须核对序号，旧结果不得覆盖新命令。

### 8.3 优先级和打断

| 新命令 | 必须执行的打断 |
| --- | --- |
| `Move` | 取消编队攻击和所有成员追击，生成新移动槽位 |
| `AttackGroup` | 取消纯移动路径，建立目标编队和成员目标 |
| `Hold` | 停止主动移动与追击，保留当前位置，可攻击进入射程的当前目标 |
| `Regroup` | 取消攻击，围绕当前锚点重新占据阵型槽位 |
| `FormationDeploy` | 部署阶段立即重排；战斗阶段转为重整移动 |

新命令必须在同一逻辑帧先更新编队状态，再向成员分发，不能让成员在一帧内收到互相冲突的命令。

## 9. 编队状态机

`CommanderGroupState` 至少包含：

```text
Deploying
Idle
Moving
Engaging
Holding
Regrouping
Defeated
```

合法转换：

```text
Deploying -> Idle
Idle -> Moving / Engaging / Holding / Regrouping
Moving -> Idle / Engaging / Holding / Regrouping
Engaging -> Idle / Moving / Holding / Regrouping
Holding -> Moving / Engaging / Regrouping
Regrouping -> Idle / Moving / Engaging
任意非 Defeated 状态 -> Defeated
```

`Defeated` 不可恢复。进入后必须取消成员命令、释放选择反馈、停止接受玩家输入并通知战斗胜负系统。

## 10. 编队移动落地规则

### 10.1 锚点与指挥官位置

- 指挥官是编队逻辑锚点和玩家命令主体。
- 有指挥官世界模型时，指挥官占据锚点格或专用 `CommanderSlot`。
- 尚无指挥官模型时，仍必须保留逻辑锚点；不得用某个普通士兵临时冒充稳定锚点。
- 指挥官移动到新锚点，其麾下单位移动到相对阵型槽位。
- 地图指挥官头像必须平滑跟随指挥官世界对象或逻辑锚点，不能绑定到随机成员。

### 10.2 槽位生成

当前三种阵型继续使用：

- `Vertical`：沿朝向后方形成纵列。
- `Horizontal`：沿朝向垂线展开横列。
- `Square`：以接近正方形的行列填充。

槽位必须根据 `Facing` 旋转，不能永远固定沿世界 X/Y 轴。无明确朝向时，使用本次移动方向；原地重整使用上一次有效朝向。

### 10.3 成员到槽位分配

采用稳定分配，避免每次命令交换位置：

1. 仍存活且原槽位合法的成员优先保留 `FormationSlotIndex`。
2. 新增或失去槽位的成员按 `SpawnOrder` 填补空位。
3. 同一槽位只能分配给一个成员。
4. 指挥官槽位与普通成员槽位不得重叠。

### 10.4 目标合法性与预留

发出移动命令时按以下顺序处理：

1. 根据目标锚点计算全部目标槽位。
2. 检查边界、地形、永久障碍和其他编队占用。
3. 若部分槽位无效，在目标周围按距离从近到远搜索最近完整合法锚点。
4. 找到完整方案后一次性预留槽位，再分别寻路。
5. 找不到完整方案则整条命令失败，不允许只移动一部分成员。

移动中的临时穿插可以容忍，但最终槽位不能重叠。预留系统必须区分“当前位置占用”和“目标槽位预留”。

### 10.5 速度与到达

- MVP 编队速度取所有有效移动成员 `MoveSpeed` 的最小值。
- 单位执行器接收编队速度上限，不能由快速单位独自冲出阵型。
- 成员进入自己的到达容差后视为就位；全部必要成员就位后，编队从 `Moving` 转为 `Idle`。
- 成员连续超时无法到达时，编队进入 `Regrouping` 并重新计算一次；再次失败则停止并给出“阵型受阻”反馈。

## 11. 编队攻击落地规则

### 11.1 攻击目标是敌方编队

点击敌方指挥官或任意敌方单位时：

```text
被点击对象
  -> 解析 TargetGroupId
  -> 被点击单位记录为 PrimaryTargetUnitId
  -> 当前己方编队进入 AttackGroup
```

不得把攻击命令只发送给当前某个己方士兵，也不得让其他成员各自随机攻击地图上的无关敌人。

### 11.2 成员目标分配

每名可战斗成员按下列优先级选择目标：

1. `PrimaryTargetUnitId` 仍存活且可攻击。
2. 目标编队中距离最近且可达的存活单位。
3. 目标编队指挥官仍存活时，可按单位定义或技能配置提高优先级。

目标单位死亡后，只能在同一个 `TargetGroupId` 内重选。目标编队被击败后，编队命令结束并转为 `Idle`，不得自动跨编队无限追击。

### 11.3 射程与追击

- 每个成员继续使用自己的 `AttackRange`、`AttackCooldown` 和 `AttackPower`。
- 射程内成员原地攻击；射程外成员请求编队战斗槽位，而不是直接走到敌方占用格。
- 追击必须受编队锚点约束。MVP 最大脱队距离为当前阵型包围半径加 2 格。
- 超过脱队距离的成员停止追击并执行 `Regroup`。
- 寻路失败的成员保持阵型，不得让整场战斗卡在永久 `Chasing`。

### 11.4 失败判定

MVP 指挥官编队满足任一条件即 `Defeated`：

- 指挥官战斗实体死亡。
- 没有任何存活且可执行战斗命令的成员。

如果当前版本尚无指挥官战斗实体，则只使用第二条，并在日志中明确这是临时规则。

## 12. 阵型系统改造要求

### 12.0 部署锁定原则

阵型的首要用途是部署，不是让移动或攻击命令反复重新编队。MVP 必须遵守：

- 部署阶段可以选择阵型、移动锚点和重新分配槽位。
- 点击“开始战斗”时，为每个玩家编队生成并锁定 `FormationLayoutSnapshot`。
- 快照保存阵型类型、锚点、每个槽位相对偏移，以及单位到槽位的稳定绑定。
- 战斗阶段的普通移动只平移锚点；不得重新调用阵型生成逻辑，不得修改 `FormationSlotIndex`。
- 普通移动不因方向变化自动旋转阵型，避免成员交叉换位。
- 攻击只能移动整个战斗锚点；成员不得脱离自己的锁定槽位独立追击。
- 单位死亡后对应槽位保持空缺，其他成员不得自动补位。
- 只有部署操作或玩家明确发出的 `Regroup` 才能重新生成、压缩或分配槽位。

锁定快照的最低数据为：

```csharp
FormationType Formation;
Vector2Int AnchorCell;
Dictionary<int, Vector2Int> SlotOffsets;
Dictionary<string, int> UnitSlotAssignments;
bool Locked;
```

战斗移动目标必须按 `TargetAnchorCell + SlotOffsets[FormationSlotIndex]` 计算。
如果不存在能容纳全部存活槽位的合法锚点，整条命令失败，不允许部分成员先行。

攻击时先计算能保持完整快照的战斗锚点。整编队到达后，射程内成员原地攻击；
射程外成员继续保持槽位，不得直接追向目标单位。目标移动时只允许更新整个战斗锚点。

当前 `FormationController` 是全局单例且遍历全部玩家单位。改造时可以暂时保留单例入口，但其状态必须按 `GroupId` 隔离：

```csharp
Dictionary<string, FormationRuntimeState> _statesByGroup;
```

每个编队独立保存：

```csharp
FormationType CurrentFormation;
Vector2Int Anchor;
Vector2Int Facing;
bool IsDeploying;
List<Vector2Int> ReservedSlots;
```

需要替换的行为：

- `CountPlayerUnits()` -> `CountAliveMembers(group)`。
- `ComputeAnchor()` -> 读取对应编队锚点。
- `ApplyFormation(type)` -> `ApplyFormation(groupId, type)`。
- `TryPlace(UnitView, cell)` 只能处理当前激活编队的成员。
- 切换指挥官时先隐藏上一编队预览，再显示新编队预览。

## 13. UI 的具体落地

### 13.1 选择页面

- 6 张卡片表示候选指挥官，不等同于 6 个详情面板。
- 已选卡片显示出征序号；详情面板显示 `FocusedCommanderId`。
- 左侧摘要显示当前焦点，另设名单条或在卡片上完整表达已选集合。
- 出征按钮旁显示 `已选数量/上限`。
- 名单为空、已满、数据无效时必须给出明确文字反馈。

### 13.2 战斗页面

- 为出征名单中的每名指挥官生成一个头像入口，顺序与 `RosterIndex` 一致。
- 当前激活头像使用金色高亮、选中边框或底光；不能只靠轻微透明度变化。
- 左下指挥官面板、生命值、特性和底部单位卡始终显示当前激活编队。
- 单位卡数量显示该编队当前存活数量，不再只显示初始配置数量。
- 阵型按钮只修改当前激活编队，并显示该编队自己的当前阵型。
- 地图上的选择环应围绕指挥官或编队范围；普通士兵可以有所属提示，但不能表现为独立控制对象。
- 编队命令失败时显示统一原因：`目标不可达`、`区域不足`、`阵型受阻`、`目标已失效`。

### 13.3 地图指挥官头像

#### 13.3.1 视觉组成

地图头像采用独立的世界空间 UI 或相机朝向的 Sprite，不得直接画进地面格贴图。标准结构为：

```text
CommanderMapMarker
  Portrait       // 指挥官透明头像
  Frame          // 队伍/品质边框
  SelectionRing  // 当前激活反馈
  HealthArc      // 指挥官生命或编队状态
  StateBadge     // 可选：移动、攻击、重整状态
  ClickTarget    // 独立点击区域
```

头像资源要求：

- 正方形透明 PNG，建议源尺寸不低于 `256×256`。
- 人脸位于视觉中心，头部和肩部不能贴边。
- 头像内容与队伍颜色边框分离；同一头像可复用不同阵营边框。
- 不得使用带洋红、白底或未清理边缘的中间生成图。

#### 13.3.2 尺寸和层级

- 在 `1600×900` 参考分辨率下，头像主体目标直径为 `64px`。
- 允许配置范围为 `48px` 到 `72px`，相机缩放时保持接近恒定屏幕尺寸。
- 点击区域不得小于 `72×72px`，但透明点击区不能遮挡相邻指挥官标记。
- 渲染层级高于地形、阵型格和普通单位，低于固定 HUD、弹窗和教程遮罩。
- 标记不得被地形深度遮挡；被单位模型覆盖时仍应完整可读。

#### 13.3.3 位置和跟随

- 无指挥官模型时，位置来源为 `AnchorCell` 对应世界坐标，加统一 `MarkerWorldOffset`。
- 有指挥官模型时，位置来源为 `CommanderView` 的头顶挂点，例如 `CommanderMarkerAnchor`。
- 标记在 `LateUpdate` 或事件驱动的视觉更新中跟随目标，不能修改逻辑锚点。
- 编队移动时标记平滑移动；逻辑锚点改变后不得滞留在旧格。
- 切换阵型只改变成员槽位，不应让头像跳到某个普通成员位置。

#### 13.3.4 交互优先级

地图输入按以下顺序判定：

```text
固定 HUD / 弹窗
  -> CommanderMapMarker 点击区
  -> 指挥官或普通单位拾取
  -> 地面格
```

- 点击己方头像只执行“激活编队”，不能在同一次点击中又向原编队发送移动命令。
- 点击已激活头像保持激活；是否打开详情由后续双击或独立按钮决定，MVP 单击不打开弹窗。
- 如果敌方指挥官编队显示头像，点击该头像等同于点击敌方指挥官：当前己方编队对其 `GroupId` 发出 `AttackGroup`。
- 部署阶段点击敌方头像只显示不可攻击反馈。

#### 13.3.5 状态表现

| 状态 | 地图头像表现 |
| --- | --- |
| 未激活 | 正常头像和阵营边框 |
| 当前激活 | 金色外环、稳定高亮或轻微脉冲；必须一眼可辨 |
| 移动 | 可显示小型行军箭头，不改变头像位置来源 |
| 攻击 | 可显示交战标记或目标连线 |
| 重整 | 可显示旋转或集合标记 |
| 低生命 | `HealthArc` 变为警示色 |
| `Defeated` | 立即不可点击，灰化并显示失败标记，短暂保留后隐藏 |

MVP 必须完成头像、阵营边框、当前激活反馈和失败不可点击；命令状态小图标可以后续增加。

#### 13.3.6 多头像重叠

- 编队逻辑锚点不得因为避免头像重叠而改变。
- 两个头像屏幕中心距离小于 `56px` 时，只对视觉标记应用垂直错层或扇形偏移。
- 错层顺序按 `RosterIndex` 稳定计算，不能每帧交换。
- 点击判定使用偏移后的实际头像区域，并始终解析到正确 `GroupId`。
- 头像离开屏幕后的边缘指示器不属于 MVP，后续增加时复用同一 `GroupId`。

#### 13.3.7 生命周期与性能

- 编队创建时创建标记，编队销毁时释放标记。
- 标记只能创建一次，不得在 UI 刷新时反复实例化。
- 头像、边框和状态图标优先使用对象池或稳定实例。
- 跟随更新不得产生每帧 GC 分配，也不得每帧通过名称查找编队。
- 头像点击事件只发送 `GroupId`，由统一选择控制器决定是否激活或攻击。

### 13.4 UI 更新事件

禁止每帧重新遍历所有单位刷新 UI。至少建立以下事件或等价通知：

```text
RosterChanged
ActiveCommanderChanged
GroupHealthChanged
GroupMemberCountChanged
GroupFormationChanged
GroupCommandChanged
GroupAnchorChanged
CommanderMarkerStateChanged
GroupDefeated
```

## 15. 不变量与运行时检查

开发版本必须在关键节点检查以下不变量：

```text
出征名单 ID 唯一
每个玩家单位恰好属于一个存在的 CommanderGroupRuntime
每个存活单位只占用一个当前格
每个最终阵型槽位最多分配一个成员
当前 ActiveCommanderGroupId 必须存在且未 Defeated
每个未失败玩家编队恰好拥有一个绑定正确 GroupId 的地图头像
单位执行命令的 Sequence 不得落后于编队当前 Sequence
Defeated 编队不得接受新命令
```

违反不变量时输出包含 `GroupId`、`UnitId`、命令序号和格子坐标的错误日志，不得只输出“操作失败”。

## 16. 分阶段实施与兼容要求

### 阶段 A：多指挥官选择与传递

- 完成多选 UI、名单快照和战斗读取。
- 暂时允许每个编队仅生成逻辑数据，但不得破坏现有单指挥官出征。

验收门槛：选择两名以上指挥官后，战斗日志能按顺序列出完整名单。

### 阶段 B：归属与多编队生成

- 建立编队注册表和单位归属。
- 为每个编队创建地图指挥官头像并绑定锚点。
- 为每个编队分配独立区域并生成成员。

验收门槛：所有玩家单位都有有效 `CommanderGroupId`，不存在重叠出生格；每个玩家编队在地图上有且只有一个可点击头像。

### 阶段 C：编队选择与 UI 切换

- 点击指挥官、成员或头像都能激活正确编队。
- 面板、单位卡和阵型状态同步切换。

验收门槛：切换编队不会改变成员归属，也不会把命令发给上一编队。

### 阶段 D：编队移动

- 建立 `GroupCommand`、锚点、槽位、目标预留和整体到达判定。

验收门槛：一次地面点击使当前编队全部成员移动，其他编队保持原命令。

### 阶段 E：编队攻击

- 以敌方编队为目标，完成成员目标分配、追击限制和同编队重选。

验收门槛：一次敌方点击使当前编队可战斗成员共同响应，目标编队失败后统一停火。

### 阶段 F：异常、性能与存档

- 完成死亡、不可达、重整、上下文清理、事件 UI 和自动化测试。

每一阶段必须保持项目可编译、场景可进入、直接打开 `BattleScene` 的 fallback 可用；不得用一次大改同时替换所有系统后再统一排错。

## 17. 必测用例

### 17.1 选择页面

1. 依次选择 A、B、C，名单顺序为 A、B、C，三张卡显示 1、2、3。
2. 再次点击 B，B 被移除，C 序号变为 2，详情仍显示 B。
3. 名单达到上限后点击 D，名单不变并显示已满反馈。
4. 出征后 `BattleStartContext` 包含完整有序名单，不是最后点击的指挥官。

### 17.2 生成与归属

1. 两名指挥官生成两个不同 `GroupId`。
2. 每个单位的 `CommanderGroupId` 与来源指挥官一致。
3. 任意出生格只被一个单位占用。
4. 某编队生成失败时，其已创建对象和占用全部回滚，其他编队不受污染。

### 17.3 选择与移动

1. 地图显示 A、B 两个不同指挥官头像，并分别绑定正确 `GroupId`。
2. 点击 A 的地图头像只激活 A，不在同一次点击中触发移动。
3. 点击 A 的任意成员后激活 A，点击空地只移动 A。
4. A 移动时头像跟随 A 的指挥官对象或逻辑锚点，不跟随随机士兵。
5. 切换到 B 后下达移动，A 保持上一命令或当前位置。
6. 阵型靠近地图边缘时自动修正完整锚点，不丢下部分成员。
7. 完整阵型无合法位置时整条命令失败，无成员擅自移动。
8. 连续快速点击两个目标时，只执行较新的 `Sequence`。

### 17.4 攻击与死亡

1. 点击敌方任意成员后，己方当前编队以其所属敌方编队为目标。
2. 近战和远程成员按各自射程行动，但不攻击无关编队。
3. 主目标死亡后在同一敌方编队内重选。
4. 目标编队失败后全部成员结束追击。
5. 当前指挥官编队失败后自动清除激活状态并切换到下一支可用编队；没有可用编队时触发失败判定。

### 17.5 UI 与上下文

1. 切换指挥官后姓名、生命、特性、存活单位数量和阵型全部同步。
2. 当前激活编队的地图头像具有清晰高亮，上一头像立即恢复普通状态。
3. 两个头像靠近时只发生视觉错层，编队锚点和点击映射不改变。
4. 编队失败后对应地图头像不可点击，并按失败表现隐藏。
5. 返回选择页面后名单恢复符合生命周期规则。
6. 直接打开战斗场景时只创建一个明确标记为 fallback 的调试编队和对应头像。

## 18. 完成定义

只有同时满足以下条件，才能声明“指挥官编队玩法已完成”：

- 选择页面真正保存多名指挥官，而不是只做多个高亮。
- 战斗按名单创建多个独立编队和单位归属。
- 地图上每个玩家指挥官都有可识别、可点击、可跟随锚点的头像标记。
- 玩家不能直接向单个士兵下达移动或攻击命令。
- 当前编队的移动、攻击、阵型和 UI 均与其他编队隔离。
- 连续命令、目标死亡、不可达、成员死亡和编队失败能够收敛到明确状态。
- 必测用例通过，编译无错误，场景无缺失引用和异常日志。
