# 指挥官编队玩法完善规则

## 1. 规则目的

本规则用于统一《指挥大师》的核心操作模型，指导后续指挥官选择、出征编组、战斗选择、移动、攻击、阵型、UI 和存档系统的开发。

游戏不得把玩家的核心操作实现为逐个士兵移动或逐个士兵攻击。玩家下达命令的最小单位是“指挥官及其麾下部队”。

## 2. 核心概念

### 2.1 指挥官

指挥官是玩家可以选择和下达命令的主体。每名指挥官拥有自己的生命值、特性、阵型配置、初始兵种和麾下单位。

### 2.2 指挥官编队

一名指挥官与其麾下全部单位共同组成一个指挥官编队。指挥官编队是战斗中的完整移动和攻击单位。

### 2.3 出征队伍

玩家在指挥官选择页面选择多名指挥官后，这些指挥官共同组成一次战斗的出征队伍。

“可以同时选择多个指挥官”专指在出征前的指挥官选择页面，将多名指挥官加入出征队伍，不代表战斗中默认同时控制多名指挥官。

## 3. 指挥官选择页面

1. 指挥官选择页面必须允许玩家把多名指挥官加入同一次出征队伍。
2. 每个出征槽位只能容纳一名指挥官，同一名指挥官不能重复加入。
3. 最大出征人数必须由配置数据决定，不得散落硬编码在多个 UI 或战斗脚本中。
4. 玩家可以添加、移除、替换指挥官，并查看每名指挥官的特性、生命值和初始部队。
5. 被选指挥官必须具有明确的已选状态、槽位位置和选择顺序。
6. 点击“出征”前必须验证：至少选择一名指挥官、没有重复指挥官、所有指挥官数据有效。
7. 进入战斗时，完整传递出征队伍，而不是只传递当前详情面板中的最后一名指挥官。
8. 返回选择页面时，应恢复尚未开始战斗的选择状态；完成或放弃战斗后的恢复方式由存档规则决定。

## 4. 战斗中的选择规则

1. 战斗开始后，为出征队伍中的每名指挥官创建一个独立指挥官编队。
2. 玩家通过点击指挥官头像、指挥官模型或编队允许的选择区域，激活一名指挥官。
3. 默认一次只激活一名指挥官。切换指挥官时，取消上一名指挥官的玩家输入焦点。
4. 选择页面的“多名指挥官出征”不得错误实现为战斗中的默认多选操作。
5. 除非后续玩法另行明确增加群体命令，战斗中不得通过 `Shift`、框选等方式同时激活多名指挥官。
6. 普通士兵不得成为独立的玩家选择对象；点击士兵时，应选择其所属指挥官编队，或仅显示单位信息。
7. 当前激活的指挥官、所属单位、可执行命令和选中反馈必须清晰可见。

## 5. 移动规则

1. 玩家点击移动目标后，移动命令下达给当前激活的指挥官编队。
2. 指挥官和麾下单位必须整体移动，不能只移动被点击的某个士兵。
3. 指挥官编队以编队锚点和阵型槽位计算目标位置，每个单位移动到自己的目标槽位。
4. 移动过程中应尽量保持阵型；受地形、碰撞或寻路影响暂时散开时，应进入重整状态并回到阵型。
5. 编队移动速度默认受编队中有效单位的最低可用速度约束，除非指挥官技能或阵型规则另有配置。
6. 目标位置不可达时，不得让部分单位无限行走或脱离编队；应拒绝命令、选择最近有效位置或给出明确反馈。
7. 指挥官死亡、眩晕、撤退或无法行动时，编队移动能力必须按照对应状态规则处理。

## 6. 攻击规则

1. 玩家指定敌方目标或攻击位置后，攻击命令下达给当前激活的指挥官编队。
2. 麾下所有仍可战斗的单位共同响应攻击命令，不得只有被点击或距离最近的一个己方单位响应。
3. 每个单位仍独立计算射程、攻击间隔、弹道、伤害、命中和死亡，但它们共享编队级攻击意图。
4. 不在射程内的单位应在保持阵型意图的前提下进入有效攻击位置，而不是无视命令或各自任意寻敌。
5. 目标死亡、失效或不可达后，由编队统一结束、重新选择目标或等待下一条命令。
6. 自动索敌只能作为编队命令的执行细节，不得越过玩家的指挥官级命令范围无限追击。
7. 攻击命令、移动命令、停止命令和重整命令的打断优先级必须集中定义。

## 7. 单位归属与生命周期

1. 每个战斗单位必须有唯一且稳定的所属指挥官标识。
2. 单位生成时加入所属指挥官编队，死亡、撤退或移除时从编队有效成员列表中注销。
3. 不允许单位同时属于多个指挥官，也不允许正常战斗单位没有所属指挥官。
4. 指挥官编队负责维护成员列表、阵型槽位、当前命令、当前目标和整体状态。
5. 单位脚本负责执行自己的移动、攻击、受击和动画，不直接读取玩家输入。
6. 玩家输入不得绕过指挥官编队直接调用单个单位的移动或攻击接口。

## 8. 推荐系统边界

后续实现应保持以下调用方向：

```text
玩家输入
  -> 当前激活的指挥官
  -> 指挥官编队命令
  -> 阵型与目标分配
  -> 麾下单位分别执行
```

建议职责划分：

- `ExpeditionRoster`：保存选择页面确定的出征指挥官列表。
- `CommanderGroup`：维护一名指挥官及其战斗单位、阵型和当前命令。
- `CommanderSelectionController`：负责战斗中单个指挥官的激活与切换。
- `GroupMovementController`：计算编队锚点、阵型槽位和整体移动。
- `GroupCombatController`：管理编队攻击意图、目标和成员攻击状态。
- `UnitBase`：执行分配给自己的行为，不处理玩家级选择逻辑。

类名可以遵循项目现有命名调整，但职责边界不得退回单兵直接控制。

## 9. UI 规则

### 9.1 选择页面

- 显示可用指挥官列表、出征槽位、已选状态和人数上限。
- 指挥官详情面板只负责展示当前查看对象，不等同于最终出征名单。
- 出征按钮应根据名单有效性启用或禁用。

### 9.2 战斗页面

- 为每名参战指挥官提供可切换的头像或状态入口。
- 当前激活指挥官必须有明确高亮，其他参战指挥官保持可见但不接收当前命令。
- 指挥官信息面板显示该指挥官编队的整体状态和麾下单位情况。
- 地图选中框、移动预览、攻击目标线和阵型范围都应属于当前指挥官编队。
- 不显示会让玩家误以为可以直接控制单个士兵的选择反馈。

## 10. 数据与存档规则

1. 出征队伍应按稳定的指挥官 ID 保存，不得只保存界面索引或对象引用。
2. 进入战斗时，根据出征名单创建运行时指挥官编队实例。
3. 指挥官配置数据与战斗运行时状态分离，避免战斗减员直接污染原始配置资产。
4. 需要保存战斗中状态时，应至少记录指挥官 ID、生命值、有效成员、阵型、位置和当前阶段。

## 11. 禁止实现

- 禁止把单个士兵作为玩家移动和攻击命令的最终接收者。
- 禁止在选择页面只保留最后一次点击的指挥官而丢失其他出征成员。
- 禁止把“多名指挥官出征”自动解释成战斗中的多指挥官同时选择。
- 禁止让同一指挥官麾下单位收到互相冲突的玩家级命令。
- 禁止通过场景查找或 UI 层级临时推断单位归属；归属必须来自明确数据。
- 禁止在 UI、战斗控制器和单位脚本中分别维护互不一致的出征名单。

## 12. 开发顺序

1. 先完成出征名单数据结构和选择页面多指挥官槽位。
2. 再完成战斗场景按名单生成多个指挥官编队。
3. 完成战斗中的单指挥官激活与切换。
4. 将现有单兵移动入口改为编队移动命令。
5. 将现有单兵攻击入口改为编队攻击命令。
6. 完成阵型保持、重整、不可达处理和目标失效处理。
7. 最后完善 UI 状态、动画、音效、存档和数值平衡。

不得先堆叠更多单兵控制功能，再在表面增加指挥官 UI。

## 13. 验收标准

完成相关功能时，至少验证以下场景：

1. 选择页面可加入两名以上不同指挥官并正常出征。
2. 战斗场景正确生成名单内的全部指挥官及各自部队。
3. 战斗中点击不同指挥官可以切换当前控制对象。
4. 点击某个士兵不会只控制该士兵。
5. 对当前指挥官下达移动命令后，其麾下有效单位整体移动并保持或恢复阵型。
6. 对当前指挥官下达攻击命令后，其麾下可战斗单位共同响应。
7. 切换指挥官后，新命令不会错误发送给上一名指挥官的部队。
8. 单位死亡、目标死亡、目标不可达和指挥官失效时，编队状态能够正确收敛。
9. 选择页面的多指挥官名单、战斗运行时编队和 UI 显示保持一致。

## 14. 变更规则

如果后续需要增加战斗中的多指挥官群体选择、指挥官合并编队、单位转属或分队操作，必须先更新本规则，明确输入方式、命令优先级、UI 反馈和数据归属，再修改代码。
