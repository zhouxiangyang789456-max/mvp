# 战斗结算商店与特性装配页面方案

## 1. 页面定位

本页面是关卡通过后进入的“结算整备商店”，同时承担五项功能：

- 展示关卡结算获得的金币。
- 从三个随机特性卡中购买一张或多张。
- 支付金币刷新商店候选卡。
- 管理玩家已经拥有的特性卡。
- 为本次出征的指挥官装备、替换或卸下特性。

它不是只有一行奖励文字的普通结算弹窗，而是战斗与下一关之间的整备页面。胜负判定和自动跳转不在本文实现范围内；页面只提供明确入口，例如：

```csharp
OpenShop(SettlementShopOpenArgs args)
```

上游在确认“关卡通过”后调用该入口即可。

## 2. 核心规则

### 2.1 特性卡是独立实例

项目当前 `CommanderDefinition.Traits` 是静态字符串列表，不能直接承担购买、出售和拖拽归属。新增两层数据：

- `TraitCardDefinition`：卡牌模板，定义名称、图标、品质、效果、价格和标签。
- `TraitCardInstance`：玩家拥有的卡牌实例，具有唯一 `InstanceId` 和当前归属。

同一种特性可以存在多个实例。购买、出售、装备和卸下始终操作 `InstanceId`，不能只用特性名称定位。

### 2.2 卡牌归属唯一

每张卡牌任何时刻只能处于一种位置：

```text
ShopOffer       商店候选，尚未拥有
Inventory       我的卡牌
Equipped        某位指挥官的某个特性槽
Sold            已出售，不再存在于本局库存
```

装备后的卡牌仍属于玩家，但从“我的卡牌”主列表移出，显示在对应指挥官槽位中。为了方便识别，左侧可开启“包含已装备”筛选；已装备卡以只读缩略项显示，并在卡牌左侧叠加装备者头像。未装备卡不显示头像。

### 2.3 指挥官拥有四个特性槽

- 每位出征指挥官固定显示四个特性槽。
- 空槽接受库存卡牌拖入。
- 已占用槽接受另一张库存卡时触发替换：旧卡回到库存，新卡进入该槽。
- 已装备特性可拖回“我的卡牌”区域完成卸下。
- 不允许同一卡牌同时装备给多名指挥官。
- 是否允许同一指挥官装备两个相同特性，由卡牌定义的 `StackPolicy` 决定。
- 指挥官阵亡不删除装备；商店整备仍可查看和调整其特性，是否允许下一关出征由其他系统决定。

### 2.4 商店候选

- 页面中心固定三个候选位。
- 每个候选显示图标、名称、效果描述、品质、价格和购买状态。
- 玩家金币足够且背包未达到上限时可以购买。
- 购买成功后候选位标记“已购买”并不可重复购买；本轮不自动补位。
- 刷新会替换所有未购买候选；已购买空位也重新生成候选。
- 刷新价格由配置决定，可固定，也可随本次商店刷新次数递增。
- 随机结果由本次商店种子决定，重新打开同一个未确认页面不能通过反复进出刷结果。

### 2.5 出售

- 右侧为明确的出售投放区。
- 库存卡可拖入出售区。
- 已装备卡不能跨过卸下步骤直接出售；先拖回库存，再拖入出售区，减少误操作。
- 放入出售区后先显示卡牌名称与售价确认，不在指针进入区域时立即销毁。
- 确认出售后卡牌移除并增加金币。
- 取消出售时卡牌回到拖拽起点。
- 出售价通常为购买基础价的一定比例，具体比例由配置决定。

## 3. 页面布局

参考 `完整ui演示.png`，页面采用上方商店、下方指挥官整备的结构。

### 3.1 顶部公共栏

- 左侧：设置按钮、金币图标和当前金币。
- 中间：页面标题“商店”。
- 右侧：部队、卡牌入口；进入子页面后返回商店时保留未确认事务。
- 商店主面板不铺满屏幕，背景仍可看到结算后的世界地图，但使用暗色遮罩降低干扰。

### 3.2 左侧“我的卡牌”

- 使用竖向滚动列表，不用固定只能显示五张。
- 每项保持稳定宽高，包含卡背或图标、品质边框和数量信息。
- 同定义卡牌默认按实例展示，后续可以提供叠放视觉，但拖拽时必须展开到具体实例。
- 已装备卡若在“包含已装备”筛选中显示，左侧叠加圆形指挥官头像。
- 该已装备项只是同一实例的镜像入口，不是库存中的第二份卡；拖动它等同于从对应指挥官槽开始卸下。
- 空库存显示简洁空状态，不生成假的占位卡。
- 整个列表区域是卸下特性的有效投放目标。

### 3.3 中央候选区

- 三张候选卡水平排列，视觉权重最高。
- 卡牌正文必须在卡面内完整显示，长描述使用受控字号和行数，不能溢出。
- 卡牌下方独立显示价格；金币不足时价格变为警示色，购买交互禁用。
- 品质标识固定在相同位置，不因描述长度发生位移。
- 已购买位保留轮廓并显示购买状态，避免用户误以为页面加载失败。

### 3.4 右侧出售区

- 常态显示“拖至此处售卖”和钱袋符号。
- 合法拖拽悬停时高亮边框并预览售价。
- 非法拖拽时显示禁止状态，不接收对象。
- 确认中的待售卡显示在区域内，其他出售拖拽暂时锁定。

### 3.5 商店底栏

- 左侧：刷新按钮和刷新费用。
- 中间：本关结算金币，例如“获得金币 ×10”；该奖励进入页面前已经记账，只作为结果展示。
- 右侧：确认按钮。
- 确认时提交本页面最终装备和库存快照，随后由上游流程决定去向。

### 3.6 指挥官特性区

- 位于页面最底部，横向显示本次出征的所有指挥官。
- 每个指挥官面板包含头像、姓名可选显示和四个稳定特性槽。
- 参考 `指挥官特性面板.png`，头像突出面板边缘，特性槽采用 2×2 布局。
- 每个槽始终保留固定尺寸；空槽显示弱化轮廓，装备后显示图标和名称。
- 指挥官数量超出横向空间时使用横向滚动或分页，不缩小到无法阅读。
- 拖动库存卡时，所有合法槽位统一高亮；不合法槽位显示原因。
- 拖拽开始后冻结指挥官面板的分页、滚动吸附和自动重排，保证目标槽不会在指针下移动。

## 4. 拖拽交互

### 4.1 拖拽上下文

所有拖拽共享 `TraitDragContext`：

```text
CardInstanceId
SourceType
SourceCommanderId
SourceSlotIndex
PointerId
TransactionId
```

拖拽显示的是专用拖拽虚影，原 UI 项只进入半透明占位状态，不把原节点直接移出布局。

### 4.2 合法路径

```text
Inventory -> CommanderSlot     装备
CommanderSlot -> Inventory     卸下
Inventory -> CommanderSlot     替换已有特性
Inventory -> SellZone          请求出售
```

商店候选卡使用点击购买，不直接拖到指挥官槽。购买后先进入库存，再由玩家决定装备给谁，保持购买和装备两个动作清晰分离。

### 4.3 取消与失败

- 松手位置无效、按取消键、页面失焦或目标在拖动中失效时，恢复源位置。
- 金币变化、槽位变化或卡牌被其他事务占用时，提交前重新验证。
- 动画只在事务成功后播放；失败时显示原因并恢复 UI。
- 同一张卡在事务完成前锁定，不能同时参与出售和装备。

## 5. 数据模型

建议新增：

```csharp
sealed class TraitCardDefinition
{
    string Id;
    string DisplayName;
    string Description;
    string IconAssetId;
    TraitRarity Rarity;
    int BuyPrice;
    int SellPrice;
    TraitStackPolicy StackPolicy;
    List<TraitModifier> Modifiers;
}

sealed class TraitCardInstance
{
    string InstanceId;
    string DefinitionId;
    TraitCardLocation Location;
    string EquippedCommanderId;
    int EquippedSlotIndex;
}

sealed class CommanderLoadoutSnapshot
{
    string CommanderId;
    string[] TraitCardInstanceIds = new string[4];
}

sealed class PlayerProgressionSnapshot
{
    int Gold;
    List<TraitCardInstance> TraitInventory;
    List<CommanderLoadoutSnapshot> CommanderLoadouts;
}
```

`CommanderDefinition.Traits` 继续表示初始模板特性，不直接被商店修改。进入一局或读取存档时，将初始特性转换为初始卡牌实例或基础不可拆卸特性；两种方案必须选定一种，不能同时让静态字符串和运行实例共同决定战斗效果。

## 6. 商店会话

新增 `SettlementShopSession`，页面打开时从玩家进度创建草稿：

```text
SessionId
RandomSeed
GoldDraft
InventoryDraft
LoadoutDrafts
Offers[3]
RefreshCount
PendingSale
DirtyVersion
BaseProgressionVersion
CommittedProgressionVersion
SessionState
```

- 页面所有操作先修改草稿。
- 每项操作仍立即在草稿内结算金币，方便玩家连续购买、刷新和出售。
- 点击确认后一次性写回 `PlayerProgressionSnapshot`。
- 意外关闭时默认保留会话并再次打开；若要放弃，必须走明确的放弃确认流程。
- 确认提交必须幂等，同一 `SessionId` 不能重复发放关卡金币或重复写入购买结果。

### 6.1 会话版本与恢复

- `BaseProgressionVersion` 是打开页面时玩家进度版本；最终提交前必须重新比较。
- 若永久进度已被其他页面修改，禁止直接覆盖，进入冲突处理：重新载入、合并允许字段或要求用户返回。
- 会话草稿每次成功事务递增 `DirtyVersion`，UI 只刷新收到的新版本。
- 结算奖励使用独立 `RewardGrantId` 记账；它与商店 `SessionId` 都必须幂等。
- 页面意外关闭后恢复同一会话时保留种子、候选、刷新次数、金币草稿和装配草稿。
- 会话完成提交后写入 `CommittedProgressionVersion` 并进入只读 `Committed`，重复确认只返回上次结果。

### 6.2 会话内存模型

- 草稿不完整深拷贝所有定义数据，只复制可变的金币、实例归属、四槽 ID、候选和版本。
- `TraitCardDefinition` 与图标资源保持只读共享引用。
- 实例索引同时维护 `InstanceId -> InstanceDraft` 和按位置划分的 ID 列表，不能每次操作扫描全部卡牌。
- 指挥官槽位用固定长度数组，装备者反向索引用于快速显示头像和校验唯一归属。
- 页面进入 `Suspended` 时只释放 UI 引用、操作锁和异步请求句柄，保留可序列化草稿与必要索引；会话进入 `Committed` 或明确 `Abandoned` 后才彻底清理草稿和反向索引。

## 7. 原子事务

所有操作统一经过：

```text
Validate -> Prepare -> Lock -> Commit -> RefreshViews -> Unlock
```

每个事务带 `TransactionId`、`SessionId`、`ExpectedDirtyVersion` 和状态：

```text
Created -> Validated -> Prepared -> Committed
                    -> Cancelled
                    -> Failed
```

同一会话一次只允许一个写事务。输入事件可以排队，但经济和归属操作不并行执行。拖拽移动过程不是事务，只有松手产生一次事务请求。

### 7.0 提交原则

- `Validate` 只读；`Prepare` 计算差异集，不修改草稿。
- `Lock` 锁定涉及的卡实例、候选位、指挥官槽和金币账户。
- `Commit` 在内存中一次应用差异并递增版本，不在中途发送 UI 事件。
- `RefreshViews` 根据差异集只刷新受影响视图，不全量重建页面。
- 事件订阅者抛异常不能回滚已经完成的经济事务；记录一次错误并继续解锁。
- 事务失败恢复拖拽来源和焦点，但不得播放成功动画或金币变化动画。

### 7.1 购买

检查候选存在、尚未购买、金币足够和库存容量；成功后扣金币、创建卡牌实例、加入库存并标记候选已购买。任一步失败都不扣金币。

### 7.2 刷新

检查金币和页面无拖拽/出售确认；扣除刷新费用后用 `SessionSeed + RefreshCount` 生成新候选。随机池需支持品质权重、重复限制和无效定义过滤。

### 7.3 装备与替换

锁定来源实例和目标槽，检查指挥官、槽位、重复限制；若目标有旧卡，则先准备将旧卡退回库存，最后一次提交两个归属变化。

### 7.4 卸下

检查卡牌仍属于该指挥官槽，提交后清空槽位并把实例改为库存状态。

### 7.5 出售

检查卡牌位于库存、未锁定且可出售；确认后增加金币并将实例从库存移除。已装备卡和基础不可拆卸特性不能出售。

### 7.6 最终存档提交

确认页面时采用两层提交：

1. 冻结会话，不再接受新事务。
2. 校验实例唯一归属、四槽引用、金币非负、候选购买状态和进度版本。
3. 生成紧凑 `ProgressionChangeSet`，只包含变化字段。
4. 写入临时存档或内存新快照。
5. 存档写入成功后原子替换当前进度版本。
6. 标记 `SessionId` 和 `RewardGrantId` 已提交。
7. 才允许关闭页面和进入后续流程。

写盘失败时保持会话草稿和 UI，不退出页面；用户可以重试。不得出现页面已关闭但购买和装备结果未保存的状态。

### 7.7 撤销边界

- 普通购买、刷新和已确认出售默认不可撤销，但页面可在操作前显示明确费用。
- 装备、替换和卸下可以继续反向拖拽，不需要建立通用撤销栈。
- 若未来增加撤销，必须记录差异集和金币变化，不通过重新运行随机逻辑恢复。

## 8. 特性生效规则

- 特性效果由 `TraitModifier` 数据驱动，不在 UI 文本中解析数值。
- 战斗开始时根据指挥官四个槽生成不可变 `CommanderTraitRuntimeSnapshot`。
- 商店中调整特性不会回写已经结束的战斗对象。
- 同一属性加成按明确顺序计算：基础值、固定加值、百分比加值、条件倍率、最终限制。
- 条件特性需要事件或低频状态更新，不允许每帧扫描所有单位。
- UI 描述通过本地化模板读取同一份效果参数，避免文本与实际数值不一致。

## 9. 页面状态

```text
Opening
Ready
Dragging
ConfirmingSale
Refreshing
Committing
Closed
```

- `Dragging` 时禁止刷新、确认和切换会破坏源对象的页面。
- `ConfirmingSale` 时只接受确认或取消出售。
- `Refreshing` 和 `Committing` 时锁定所有经济操作。
- 状态切换必须有唯一入口，不能由多个按钮分别修改锁定标记。

## 10. 反馈与可用性

- 金币变动使用短暂数值反馈，但最终金币始终显示固定位置。
- 合法投放为金色或绿色边框；非法投放为红色并显示简短原因。
- 特性卡悬停显示完整效果、品质、售价和当前装备者。
- 鼠标和触控都使用统一 Pointer 拖拽接口。
- 点击卡牌也提供“装备到”“卸下”“出售”菜单，作为拖拽的可访问性替代方式。
- 确认离开前若有待处理出售或拖拽，先结束当前交互。

## 11. 性能与生命周期

- 三个商店候选和指挥官四槽数量固定，使用预创建视图，不反复销毁重建。
- 库存列表使用视图复用或虚拟化，避免卡牌数量增长后生成大量 GameObject。
- 拖拽虚影全页面只复用一个实例。
- 图标和头像按 AssetId 缓存，页面隐藏时释放视图对会话的引用，但 `Suspended` 会话由会话仓库继续持有；正式提交或放弃后再释放会话数据。
- 金币和卡牌变化采用事件驱动更新，不在 `Update` 中轮询进度数据。
- 排序和筛选只在库存版本变化时执行，复用列表缓冲。
- 页面关闭时退订事件、取消拖拽、清理锁和未完成动画。

### 11.1 库存虚拟化

- 列表数据源只保存排序后的 `InstanceId`，可见视图数量为“屏幕可见项 + 前后缓冲项”。
- 滚动只重新绑定跨过边界的视图，不重建全部卡牌节点。
- 每个视图记录 `BoundInstanceId` 和 `BindGeneration`；异步图标返回时必须同时匹配两者。
- 拖拽开始后将源视图标记为 `Pinned`，虚拟列表不得回收；列表中保留同尺寸占位。
- 拖拽结束后解除固定并按当前滚动位置重新绑定。
- 排序或筛选变化时保持选中实例 ID；若该实例不再可见，再按规则清除选中状态。
- “包含已装备”镜像项仍绑定原 `InstanceId`，不能创建第二份实例数据。

### 11.2 Canvas 与布局

- 商店主面板、库存滚动区、拖拽层、指挥官区和浮层尽量拆成独立 Canvas，避免金币变化重建整个页面。
- 稳定区域不用每帧 `LayoutGroup` 和 `ContentSizeFitter` 重新计算；初始化后写入固定尺寸或只在数据版本变化时布局。
- 拖拽虚影放在专用顶层 Canvas，只更新一个 `RectTransform`，不触发原列表重排。
- 特性描述和价格文本仅在绑定变化时设置；避免反复写入相同字符串触发 TMP 网格重建。
- 合法槽高亮批量切换，不为每个槽启动独立协程或 Animator。
- 金币动画更新显示层，不在动画每帧修改真实经济数据。

### 11.3 资源加载与缓存

- 图标、头像和边框请求使用 `AssetId + LoadGeneration`；页面关闭或视图重绑后旧回调只释放句柄。
- 页面打开前预加载三个候选卡、当前可见库存和出征指挥官头像；不可见库存图标按滚动按需加载。
- 缓存设置容量上限和引用计数，不能因多次进入商店无限持有 Sprite。
- 同一 AssetId 的并发请求合并为一个加载任务，完成后分发给仍有效的订阅者。
- 缺失资源使用稳定占位图，不在每次绑定时重复输出警告。

### 11.4 排序、筛选与搜索

- 库存变化使用脏标记，排序最多执行一次；连续购买或装备事件在本帧末尾合并刷新。
- 比较键提前缓存品质序号、名称排序键、装备状态和获得顺序，比较器中不查询资源和本地化系统。
- 筛选先处理 ID 列表，不创建新的卡牌实例对象。
- 默认不在每次拖拽悬停时重新排序；事务完成后再更新顺序，避免目标项跳动。

### 11.5 拖拽与射线

- 使用 EventSystem 的开始、移动、结束事件，不在全页面 `Update` 中轮询鼠标。
- 拖拽时只检测注册的出售区、四槽和库存卸下区，不对所有 UI 节点执行自定义扫描。
- 非交互装饰关闭 `Raycast Target`，降低 GraphicRaycaster 候选数量。
- 合法性在目标变化时计算一次；指针仍停留同一目标时复用结果。
- Pointer 取消、窗口失焦、场景切换和页面禁用统一调用同一个 `CancelDrag`。

### 11.6 事件与增量刷新

事务提交发布紧凑 `ShopChangeSet`：

```text
GoldChanged
ChangedOfferIndices
AddedInventoryIds
RemovedInventoryIds
ChangedInstanceIds
ChangedCommanderSlots
InventoryOrderDirty
```

各视图只消费相关字段。禁止在一次装备操作后同时全量刷新库存、三张候选和所有指挥官面板。事件在事务解锁前按固定顺序排队，解锁后一次分发，防止订阅者重入事务。

### 11.7 页面异步生命周期

- 页面具有递增 `ViewGeneration`；所有加载、动画、存档和延迟回调保存创建代次。
- 页面关闭后旧代次回调不得访问视图，也不得重新打开浮层。
- `Opening` 期间再次请求打开同一 Session 只合并请求，不创建第二套页面。
- `Committing` 期间关闭请求转为“提交完成后关闭”，不能强行销毁会话。
- 切换场景前先取消拖拽和浮层，再停止接收事务，等待或取消可取消加载，最后释放视图。

### 11.8 初始性能预算

- 页面静止时脚本 `Update` 数量接近零，稳态 `GC Alloc` 为每帧 `0 B`。
- 普通购买、装备、卸下和出售的主线程逻辑目标小于 `1 ms`，不包含异步资源和存档 I/O。
- 滚动库存时不得因视图创建产生持续 GC；视图池外创建次数在预热后为零。
- 单次操作只重绑受影响卡牌和槽位；全页面 Canvas rebuild 不应成为常态。
- 100、300、1000 张卡牌规模下，场景 GameObject 数量主要由可见视图决定，不与库存总量线性增长。
- 存档写入不得阻塞拖拽帧；确认阶段可以显示等待状态，但主线程不能同步执行长时间磁盘 I/O。

## 13. 开发顺序

### 阶段 1：数据基础

1. 建立特性定义、卡牌实例、库存、金币和四槽装配数据。
2. 明确现有静态 `Traits` 的迁移策略。
3. 建立商店会话和确定性随机种子。
4. 先用纯 C# 调用完成购买、刷新、装备、卸下、出售和最终提交，不依赖 UI 节点。

### 阶段 2：静态页面

1. 使用现有美术元素搭建顶部商店和底部指挥官面板。
2. 完成三候选、库存、出售区、刷新、金币和确认显示。
3. 验证 16:9、4K 和较小窗口下无裁切与重叠。
4. 建立独立 Canvas、视图池、异步资源代次和统一页面状态机。

### 阶段 3：经济事务

1. 实现购买、刷新和出售确认。
2. 验证金币不足、库存满、重复提交和重新打开会话。
3. 实现 `ShopChangeSet` 增量刷新与最终存档两层提交。

### 阶段 4：装备拖拽

1. 实现库存到指挥官槽、槽到库存和槽位替换。
2. 增加装备者头像、合法目标高亮和失败回退。
3. 增加点击菜单替代路径。

### 阶段 5：特性生效

1. 将装配结果转为下一场战斗的运行快照。
2. 实现第一批数据驱动效果并核对 UI 描述。

### 阶段 6：性能与人工验收

1. 库存长列表复用、资源缓存和事件解绑检查。
2. 人工重复购买、刷新、替换、卸下、出售和重新打开页面。
3. 检查同一卡实例始终只有一个归属，金币账目始终守恒。
4. 使用 100、300、1000 张模拟库存人工采样滚动、筛选、拖拽和页面打开耗时。

### 13.7 执行门禁

每阶段进入下一阶段前必须满足：

- 数据层不引用具体 UI 组件、PointerEventData 或场景对象。
- 所有写操作都经过事务服务，视图不能直接修改金币、库存和槽位。
- 编译为 0 错误、0 警告。
- 本阶段人工操作后，实例唯一归属和金币守恒检查通过。
- 页面关闭后无订阅、拖拽锁、待售确认和旧资源回调残留。
- Profiler 中没有因该阶段新增的持续每帧 GC 或明显 Canvas 全量重建。

若执行门禁失败，优先修复数据和事务层，不通过在 UI 层增加特殊分支绕过。

## 14. 人工验收清单

- 页面打开时关卡金币只发放一次。
- 三张候选可以独立购买，金币不足时不可购买。
- 刷新扣费准确，关闭再打开不会免费重抽。
- 未装备卡左侧无头像，已装备卡显示正确指挥官头像。
- 库存卡能装备到任意合法空槽。
- 拖到已占用槽时旧卡完整回到库存。
- 已装备特性能拖回“我的卡牌”并清空原槽。
- 已装备卡不能直接出售；库存卡出售后金币增加且实例消失。
- 无效松手、取消出售和页面失焦都能恢复原状态。
- 多位指挥官各自四槽互不串数据。
- 确认后重新进入整备页面，库存、金币和装配结果保持一致。
- 任何操作失败时不出现重复卡牌、负金币或空指针残留。
- 拖拽进行中关闭页面，卡牌回到唯一合法归属且锁被释放。
- 拖拽源项滚出可视区域时，源占位和虚影保持正确，结束后视图池恢复。
- 异步头像或图标在视图重绑后晚到，不会显示到错误卡牌或指挥官。
- 最终存档写入失败时页面保持打开，金币和装配草稿仍可重试提交。
- 连续点击购买、刷新或确认不会产生重复事务。
- 页面提交完成后重复调用确认不会重复发奖、扣费或创建卡牌。
- 外部进度版本发生变化时不会静默覆盖，而是进入明确冲突处理。
- 1000 张库存时场景只保留可见范围附近的卡牌视图，滚动期间无持续对象创建。

## 15. 执行顺序总览

### 15.1 打开页面

```text
ValidateOpenArgs
-> LoadProgressionSnapshot
-> ResumeOrCreateSession
-> ValidateDefinitions
-> PreloadCriticalAssets
-> BuildFixedViews
-> BindVisibleInventory
-> Ready
```

关键资源失败时使用占位图进入 `Ready`；进度或会话数据失败时不能开放经济操作。

### 15.2 单次操作

```text
Input
-> CreateTransaction
-> ValidateVersionAndOwnership
-> PrepareChangeSet
-> LockResources
-> CommitDraft
-> IncrementDirtyVersion
-> DispatchShopChangeSet
-> Unlock
-> PlayFeedback
```

### 15.3 确认与关闭

```text
CancelTransientInteraction
-> FreezeSession
-> ValidateDraftIntegrity
-> BuildProgressionChangeSet
-> PersistNewVersion
-> MarkSessionCommitted
-> ReleaseViewResources
-> Closed
```

关闭动作不得跳过 `FreezeSession` 和完整性验证。若只是临时隐藏页面而不提交，会话进入 `Suspended`，不释放草稿。

### 15.4 失败恢复优先级

1. 保证永久进度没有部分写入。
2. 保证卡牌实例只有一个归属。
3. 保证金币与事务记录守恒。
4. 恢复页面可继续操作或重试。
5. 最后恢复动画、选中和滚动位置等表现状态。

## 16. 完成定义

- 商店、库存、出售和指挥官四槽形成完整操作闭环。
- 卡牌实例归属唯一，所有经济和装配操作具备原子提交与失败回滚。
- 页面视觉结构与参考图一致，同时适配现有项目的指挥官数量和分辨率。
- 特性效果由数据驱动并能生成下一场战斗运行快照。
- 页面关闭和重新打开不会重复发奖、刷新候选或丢失草稿。
- 热路径无每帧轮询，库存增长后仍保持稳定布局和交互性能。
