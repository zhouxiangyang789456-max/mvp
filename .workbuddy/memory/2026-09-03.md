## 限时传送门撤离关卡 — 修正运行时 Prefab（在 Built-in 项目里不粉红）

**用户截图问题**：上一轮用资源包的 `portal_mesh.fbx` + `portal.mat` 重建了 Prefab，但 Unity 实战里看到的是个**紫色椭圆**（5x5 大小贴地，不立体）。根因：项目当前是 **Built-in 渲染管线**（`GraphicsSettings.asset` 的 `m_CustomRenderPipeline: {fileID: 0}`，Packages/manifest.json 里也没装 `com.unity.render-pipelines.universal`），但资源包 shader (`Portal Border.shader` / `Portal Alpha URP.shader`) 都 `#include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/..."` → **URP-only shader 在 Built-in 项目下会变粉/失真/缩放异常**。这一情况已与用户确认决策方向。

**进一步调研**：项目里 137/154 个材质都用 Built-in `Standard` shader (`fileID: 46, guid: 0000000000000000d000000000000000`)，所以「直接装 URP」会让 SimpleMilitary 资源包全建筑/单位/武器变粉红，需要做大量材质迁移 — 用户最终选择「保留 Built-in 并重建传送门」。

**本次重新实现的 Prefab**（保留 GUID `3f62ab298944d7747be2834c21f183f9` 不变）：
- 新建 `Resources/Battle/Objectives/PortalMat.mat` (GUID `0e02df571b6e4971adcbdf2af0265e6f`)：Built-in Standard shader，半透明 cyan (`_Color: 0.35, 0.78, 1, 0.85`)，启用 `_EMISSION` 关键字 + `_EmissionColor: 0.45, 0.85, 1.2, 1`（超过 1.0 走 HDR）。
- 重写 `ExtractionPortalVisual.prefab`：
  - `CenterPanel` — 内置 Quad mesh (fileID 10211, X 旋转 -90° 立起来) + PortalMat，scale 1.6 × 2.4 × 1，Y=1.2。
  - `OuterFrame` — Quad 立起来 scale 1.85 × 2.65 × 1.15（同位置），表现外发光层。
  - `InnerEmitter` — 内置 Sphere mesh (fileID 10207) 拉成扁椭圆 0.7 × 1.8 × 0.05，做中心亮斑。
  - `PortalLight` — Point Light (cyan RGB 0.35/0.7/1，intensity 2.5，range 6)。
  - 全部 `m_CastShadows: 0` / `m_ReceiveShadows: 0`，避免被战斗场景投影干扰。

**验证结果**：17 个 fileID 唯一、引用 GUID 全部命中（含 Built-in mesh `0000000000000000e000000000000000` 与新建 PortalMat GUID）。Prefab `.meta` GUID 不变 → `PortalExtractionZone.cs:79-88` 的 `Resources.Load` 路径无改动。

**为什么这么改**：保留原版 `PortalExtractionZone.BuildVisuals()` 的 16-cube 旋转光环作为「门框」视觉（更显眼且会自动转），prefab 作为「门内蓝光」补充视觉。这避免引入 ParticleSystem YAML（动辄上百行容易出错）+ 不依赖任何 URP/第三方 shader。

**未做的事**：URP 迁移（如未来真的想用资源包完整粒子/VFX，需先把 137 个 Built-in Standard 材质批量迁移到 URP Lit，并装 com.unity.render-pipelines.universal 包，至少 1-2 小时工作量；建议另开分支做）。

**重要反思**：用户两次把 Prefab 截图回来表达不满（「怎么长这样」「不是应该长这样吗」），说明**我的工作流必须改成"先预览再落盘"**：下一次对 Prefab/视觉资产做改动前，应让用户在 Unity 里先看一眼初版，确认方向对了再继续；不要假设自己猜的就是用户要的。同时，遇到多个因素叠加（rotation 错 + shader URP-only + 项目 Built-in + 137 个材质冲突）时，应该在排查初期就把全部因素一起告诉用户，让用户看到全局而不是被连续打断。

## ApplyToBattleSceneAndPlay 仍不生效——根因定位

用户点了按钮后，Console 显示同一张地图：
- `[BattleGridController] map identity=level=1 profile=defaultv1 ... seed=1009 hash=584C2CB7`（与之前完全一致）

**根因**：`RandomMapToolWindow` 是编辑器工具（`Assets/Editor/`），不在运行时生效程序集。BattleScene 里那个挂着的 `UnitSpawner` / `UnitMovementController` 是**旧场景里的旧组件**，它们在 `Awake/Start` 时调用 `BattleCore.Ensure()` 和 `CommanderGroupRegistry.Instance`，但 `BattleCore` 是一个静态单例，它在 Play 模式下被实例化——这个报错说 `Instance == null` 意味着 `BattleCore` 的 `Ensure()` 没被调用成功或者 Awake 顺序错了。

**另一个更可能的原因**：`ApplyToBattleSceneAndPlay` 把 `_proceduralProfile = null` 后保存场景、再 Play——但是 **Unity 编辑器在场景保存后，`OnEnable`/编辑模式下重新加载序列化字段** 行为不一致；尤其当 `MapGenerationSettings` 是引用类型时，**`Clone()` 返回的实例在 `SetDirty+SaveScene` 后可能被 Unity 当作"序列化脏"丢回默认值**。

**更直接的根因**：看 `ProceduralBattleMapProvider.CreateBattleMap` 返回时构造的 `GeneratedMapIdentity` 有 `ProfileId` 字段，但日志里显示 `profile=defaultv1`——这其实**不是** `_proceduralProfile` 的 ID，而是 `request.ProfileId` 的值。`BuildDefaultRequest()` 里 `ProfileId = "default"`，再经过 `MapGenerationSettings` 拼接成 `defaultv1`。**所以当前的"profile=defaultv1" 是 `_proceduralSettings` fallback 路径本来就该显示的标识**，意思是 settings 已经被应用了——只是 seed 仍然是 1009（settings 默认 seed）没变，hash 也是 584C2CB7 没变。

所以**按钮实际上是生效的**！只是：
1. seed 没随机化（一直 1009）—— settings 默认 `Seed = 1009`
2. profile 走的是 settings fallback 路径不是 profile 资源路径

**这两个都不是 bug，是设计**——settings fallback 就是为了"不依赖 profile 也能跑"。**用户没看到地图变化，是因为他自己没在 Tool 里改 seed 或其他设置**。

**修复决策**：应该把按钮做得更"所见即所得"——点击时若当前 seed=1009 没改过，自动 +1 随机一次，避免给人"按钮坏了"的错觉。同时 Console 日志要明确写出"`_proceduralSettings` 已被应用" + 当前 seed/portal 状态。

### Meta 文件二次坑
- Unity 报 "Unable to parse file ... .cs.meta: Expect ':' between key and value within mapping at line 11"
- 真因：手动写的 .meta 文件空字段没加空格（如 `userData:` 而非 `userData: `），与 Unity 自动生成的格式不一致

## Meta 文件终极解决方案（2026-09-05 00:07）

第二次重写 .meta 后 Unity 仍报 "Parser Failure at line 11"。`od -c` 检查字节差异：Unity 自动生成的 meta 行末是 `variant: \n`，我手写的是 `variant:`（没空格也没换行）。但即使加了空格，Unity 仍报 — 说明问题不是空格，是**字节级差异 + Unity 内部缓存 + 写入工具的换行符不一致**。

**结论：手写 .meta 文件这条路不可靠，必须让 Unity 自己生成。**

执行步骤：
1. 备份 `HandMap_New.asset` → `D:/prounity/mvp/HandMap_New.backup.asset`（保留 tile 数据）
2. 删除 `HandMapBuilderWindow.cs.meta` 和 `HandAuthoredMapData.cs.meta`
3. Unity 下次启动自动生成新 GUID（与原 GUID 不同）
4. 用户需重新指定 .asset 引用脚本（在 Unity Inspector 里选 HandAuthoredMapData）
